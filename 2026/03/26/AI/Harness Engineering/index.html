Harness Engineering

Harness Engineering

一、定义

Harness 是模型之外的一切。 Agent = Model + Harness。模型提供推理能力，Harness 提供让这种能力真正落地干活的所有外围系统：工具执行、上下文管理、记忆、安全边界、编排调度。

这个词借用了“马具”的意象：模型是一匹好马，但光有马跑不了运输；Harness 是缰绳、马鞍、道路和围栏，控制方向、划定边界，让马按人的目标拉车。

二、为什么是 2026 年

关键词的演变轨迹很清晰：2023-2024 是 Prompt Engineering（怎么跟模型说话），2025 是 Context Engineering（让模型看到什么），2026 是 Harness Engineering（搭建模型周围的整套系统）。

三个推动力：

模型的无状态性无法靠模型自己解决。 大模型本身无状态、不能执行、不能记忆、不能遵守组织规则。Agent 要跟业务系统关联、要规划分解、要记忆、要行动，这些“不能”全靠 Harness 补。

Harness 是厂商建立粘性的关键。 无状态的模型谁好就用谁；有状态的 Harness 一旦业务逻辑、记忆、工具链沉淀下来，迁移成本就高了。模型厂商把边界往外拓，Harness 绕不开。

调 Harness 比调模型便宜，效果却可能差一个量级。 LangChain 让 Nemotron 3 Ultra 跑 Deep Agents 评测，没有重新训练模型权重，只调整了系统 Prompt、工具描述和中间件，成绩就追到了与最高分闭源模型持平的水平，而单次评测成本只有后者的十分之一。这说明同一个模型放进不同 Harness，释放出的能力可以差出量级。

三、Harness 包含什么：三层 + 三特性

CCF 对话中李庆丰给出的框架是 “3+3”：三层核心能力，三个辅助特性。

三层核心

第一层：执行环境与工具管理。 让 AI 的执行贴合真实工作场景。包括工具列表、沙箱隔离（LocalShellBackend、OpenSandbox）、文件读写、命令执行。关键是“工具系统 = 工具列表 + 受控的执行环境”，不能只给工具不给边界。

第二层：上下文与记忆。 核心是提升模型的注意力——内容跟目标越精准，执行越好。包括上下文过滤/总结/检索、持久化记忆（会话进度、用户确认、历史操作）、Todo 跟踪。腾讯云的文章把这一层拆得更细：上下文精细化管“每轮看到什么”，记忆与状态管“能否连续作战”。

第三层：业务编排与多 Agent 调度。 把模型能力转化成跟业务结合的具体目标。包括执行顺序安排、子 Agent 委托、后台并行、何时等待用户确认、何时终止。

三特性

可验证性、可观测性、可治理性。 完整的执行轨迹是审计依据，也是持续优化的燃料。权限围栏、沙箱、审批策略都在这一层。CCF 对话中强调：提示注入无法在模型层可靠修复，缓解措施必须放在 Harness 中，通过控制 Agent 能访问什么、被允许执行什么来防御。

四、六层架构

层 管什么 关键问题
上下文精细化 模型每轮看到什么 过滤噪声、总结历史、按需检索
广义工具系统 工具 + 受控执行环境 沙箱边界、文件权限、命令白名单
执行编排 任务如何推进 顺序、子任务委托、等待/终止条件
记忆与状态 能否连续作战 进度、用户确认、历史决策持久化
评估与观测 过程可信吗 完整轨迹、失败原因、质量评估
约束与恢复 出错后怎么办 权限边界、自动纠错、回退、降级

五、关键工程要点

5.1 模型越强，Harness 越要做减法

CCF 对话中一个反直觉的判断：Harness 并不是去束缚模型的智能，反而要做减法——从外围让系统更可管理、可演化。模型能力越强，Harness 越应该收敛到“控制方向与边界”，而不是加更多规则去限制模型。

5.2 压缩（Compaction）是标配

长工具调用循环会撑爆上下文窗口。Microsoft 的 HarnessAgent 提供 token 预算感知的压缩策略，传入最大窗口和最大输出即可启用；也可以用自定义策略或关闭。这是 Harness 在上下文工程层面的基础能力。

5.3 工具审批是 Harness 职责，不是模型职责

Shell 执行、文件写入、外部 API 调用，这些操作的审批策略（哪些需要人工确认、哪些自动放行）由 Harness 管理。Microsoft 的 HarnessAgent 默认启用工具审批和自动审批规则，shell 命令的 deny-list 只是 UX 预过滤，不是安全边界——真正的边界在执行侧。

5.4 Harness 是 RSI 的切入点

CCF 对话中提出：现阶段模型不具备在线持续学习能力，所以自我改进先从 Harness 层动。Harness 本质是配置工程，在这一层做自动优化比改模型权重更容易。等 Harness 固化到一定程度，再进入模型本身的优化，形成“Harness ↔ 模型”的协同迭代。

六、与之前概念的层级关系

Harness 是前面所有概念的上位整合层：

概念 在 Harness 中的位置
Context Engineering Harness 的核心子问题之一（上下文精细化 + 记忆层）
Function Calling Harness 执行工具调用的底层机制
MCP Harness 连接外部工具的标准化协议层
Spec Coding Harness 在开发流程层面的实践：把约束从对话变成持久化文档

一句话：Context Engineering 管“看什么”，Function Calling 管“怎么说”，MCP 管“怎么接”，Harness 管的是这一切如何组装成一个能安全、可控、持续干活系统。

七、总结

问题 答案
Harness 是什么？ 模型之外的一切，Agent = Model + Harness
为什么火？ 模型瓶颈转移到外围；Harness 是厂商粘性载体；调 Harness 性价比极高
包含什么？ 三层：执行/工具、上下文/记忆、编排/调度；三特性：可验证、可观测、可治理
和 Context Engineering 什么关系？ Context 是 Harness 的核心子问题之一
模型越强 Harness 越复杂？ 反了，越强越要做减法，收敛到边界控制
一句话收束 模型负责推理，Harness 负责让推理安全、可控、可追溯地变成真实动作

Harness 不是让模型更聪明，而是让模型“能干活”。 它把上下文窗口当有限资源治理，把工具执行关进受控边界，把长任务拆成可恢复的步骤，把每一次决策留下可审计的轨迹。模型在变强，但 Harness 决定的是：这份智能最终能安全地释放出多少。
