学习Flutter5：状态管理

学习Flutter5：状态管理

一、什么是状态？

状态是指应用中可以变化的数据。

类型 说明 示例 作用范围
局部状态 单个页面或组件内部的状态 表单输入、开关状态、动画进度 一个 Widget
全局状态 多个页面共享的状态 用户登录信息、购物车、主题设置 整个 App

二、状态管理演进路线

三、方案

1. setState（最简单，适合局部状态）

Flutter 自带的最基础状态管理方式。

优点：

  • ✅ 简单直接，学习成本为零
  • ✅ 无需引入额外依赖

缺点：

  • ❌ 只能管理局部状态
  • ❌ 跨组件共享状态困难
  • ❌ 会导致 Widget 树重建，性能问题

适用场景：单个页面内部的简单状态、快速原型开发

2. InheritedWidget（Flutter 底层机制）

Flutter 框架底层的状态共享机制，Provider 等方案基于它实现。

优点：

  • ✅ Flutter 原生机制，性能好
  • ✅ 实现状态共享的基础

缺点：

  • ❌ 使用复杂，样板代码多
  • ❌ 容易导致不必要的重建

适用场景：理解 Flutter 底层原理（不推荐直接使用）

3. Provider（最流行，官方推荐）

Google 官方推荐的方案，基于 InheritedWidget 封装。

  1. 创建状态模型，继承 ChangeNotifier
  1. 通过 ChangeNotifierProvider 提供 (Provide) 状态
  1. 消费 Model

Provider 类型对照表：

Provider 用途
Provider 提供对象，不监听变化
ChangeNotifierProvider 配合 ChangeNotifier 使用
FutureProvider 处理异步数据
StreamProvider 处理 Stream 数据
ValueListenableProvider 配合 ValueNotifier 使用

优点：

  • ✅ 官方推荐，社区成熟
  • ✅ 学习曲线平缓
  • ✅ 性能好（精确重建）
  • ✅ 依赖注入简单

缺点：

  • ❌ 依赖 BuildContext
  • ❌ 大型项目可能变得复杂

适用场景：中小型项目、大多数应用的首选

4. Riverpod（Provider 的升级版）

由 Provider 作者开发，解决了 Provider 的所有痛点。

Provider vs Riverpod 对比：

特性 Provider Riverpod
依赖 Context ✅ 必须 ❌ 不需要
编译安全 ❌ 运行时错误 ✅ 编译时检查
测试 需要包装 直接测试
组合能力 需要 MultiProvider 自动组合

优点：

  • ✅ 不依赖 BuildContext
  • ✅ 编译安全
  • ✅ 易于测试
  • ✅ 支持异步

缺点：

  • ❌ 学习曲线稍陡

适用场景：新项目（强烈推荐）、需要高可测试性的项目

5. Bloc/Cubit（适合复杂业务逻辑）

Bloc 是 Business Logic Component 的缩写，通过事件流来管理状态。

Cubit（Bloc 的简化版）：

优点：

  • ✅ 业务逻辑清晰分离
  • ✅ 事件溯源，易于调试
  • ✅ 适合复杂业务流程

缺点：

  • ❌ 样板代码多
  • ❌ 学习曲线陡峭

适用场景：大型项目、复杂的业务逻辑、需要事件记录的场景

6. GetX（功能大而全）

集状态管理、路由管理、依赖注入于一体的全能框架。

优点：

  • ✅ 功能全面（状态+路由+依赖注入）
  • ✅ 代码简洁，样板少
  • ✅ 性能好（智能重建）

缺点：

  • ❌ 侵入性强
  • ❌ 与 Flutter 生态隔离
  • ❌ 大型项目维护困难

适用场景：快速开发、小型项目、个人项目
