【Web API】URL.createObjectURL() vs FileReader.readAsDataURL()

URL.createObjectURL() vs FileReader.readAsDataURL()

URL.createObjectURL() 和 FileReader.readAsDataURL() 都是前端处理文件（如本地图片预览）的常用方式，但它们的底层机制、性能表现和适用场景有显著差异。

核心区别对比

特性 createObjectURL readAsDataURL
同步/异步 同步 异步
结果格式 blob: URL（对内存中 Blob 对象的引用） data: Base64 字符串（包含文件数据）
速度 极快（不读内容） 较慢（读+编码）
内存占用 占用小，效率高（仅引用） 占用大（Base64 全文，体积膨胀约 33%）
生命周期 文档内有效 字符串，持久
释放内存 手动调用 URL.revokeObjectURL() 释放 自动清理，无需手动释放
能否存库/传后端 不能（仅本地引用） 可以
大文件表现 好 差（内存暴涨）
兼容性 所有浏览器均支持（包括 IE10+） 所有浏览器均支持（包括 IE10+）

如何选择

优先使用 URL.createObjectURL() 的场景

  • 大文件预览：处理大图片或视频时，它能避免生成巨大的 Base64 字符串，性能和内存表现更佳。
  • 文件下载：配合 <a download> 标签触发下载时，使用 Blob URL 兼容性更好，且不会因 Base64 字符串过长导致卡顿。
  • 需要高效能的场景：例如在循环中频繁创建预览地址时（但务必记得及时 revoke）。

使用注意：务必在图片加载完成（img.onload）或组件销毁时调用 URL.revokeObjectURL(url) 来释放内存。

使用 FileReader.readAsDataURL() 的场景

  • 需要持久化或传输数据：如果你需要将图片数据（例如用户头像）直接存入 localStorage，或者作为 JSON 的一部分发送给后端，Base64 字符串是合适的选择（注意存储大小限制）。
  • 简单的单次预览：如果不希望管理 URL 的生命周期，且文件体积较小，用它可以省去手动释放的步骤。

使用注意：读取结果是异步的，代码需要写在回调里。如果只想要纯 Base64 数据，记得去掉结果开头的 data:*/*;base64, 声明。
