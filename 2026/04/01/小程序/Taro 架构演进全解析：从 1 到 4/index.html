Taro 架构演进全解析：从 1/2 到 4

Taro 架构演进全解析：从 1/2 到 4

一句话概括：Taro 1/2 是“编译时”架构，Taro 3 是“重运行时”架构，而 Taro 4 则是在运行时架构基础上的全方位性能与生态升级。

一、Taro 1/2 vs Taro 3：架构层面的“代际差异”

Taro 1/2 与 Taro 3 可以看作是两套完全不同的框架。其核心区别在于：Taro 1/2 在编译时完成一切，Taro 3 将核心工作留到了运行时。

对比维度 Taro 1 / 2（编译时） Taro 3（重运行时）
核心原理 通过 AST 静态编译，将 React/JSX 转换为各端代码 在目标端模拟 DOM/BOM API，让框架直接运行
渲染机制 JSX → 小程序字符串模板（.wxml），性能接近原生 Virtual DOM → 模拟 DOM 树 → setData → 视图更新
框架支持 有限，主要基于 React/Nerv 广泛，支持 React、Vue、Preact 等
开发体验 JSX 语法受限，不能写太“JavaScript”的代码 可使用框架完整语法，接近 Web 开发体验
性能 优（运行时开销小） 有损耗（模拟环境 + setData 开销）
生态兼容 无法引入 Web 第三方 UI 库 可引入大量 Web 生态库

1.1 为什么 Taro 3 要改成“运行时”？

这是一次经典的 “用性能换生态” 的架构决策。Taro 1/2 的编译时模式存在三个无法解决的痛点：

  • 语法枷锁：JSX 必须静态可分析，导致无法使用动态组件、高阶组件、Math.random() 等纯 JS 特性。
  • 生态屏障：编译器基于 React JSX 编写，无法低成本支持 Vue 等其他框架。
  • UI 库不可用：Web 组件库依赖 document、getBoundingClientRect 等浏览器 API，编译时无法转换。

改为运行时后，Taro 变成了一层“多框架兼容层”——只要框架能生成 VNode，Taro 就能将其渲染到小程序。代价是性能有所下降，但换来了海量的 Web 生态和极佳的开发体验。

工程视角的额外收益：React/Vue 版本升级不再需要 Taro 团队修改编译器，Taro 核心升级频率大大降低，稳定性显著提升。

二、Taro 3 的运行时渲染机制（深入底层）

2.1 编译产出的变化：WXML 从“商品房”变成“毛坯房”

Taro 1/2 编译生成的 WXML 是最终的 UI 模板，而 Taro 3 编译生成的 WXML（如 base.wxml）是一套通用的模板骨架，里面堆满了 <template> 标签，没有任何业务 UI 的具体内容。它只负责在运行时根据数据动态拼装界面。

2.2 核心文件角色的变化

文件 Taro 1/2 的角色 Taro 3 的角色
index.js “甩手掌柜”：UI 结构被抽走，只剩数据和逻辑 “总导演”：包含 createElement 调用，是 UI 的数据生产者
base.wxml 包含最终 UI 模板 仅包含通用模板骨架，待运行时填充
.wxss 存放样式规则（不变） 存放样式规则（不变）

关键链路：index.js 运行时生成 VNode → Taro 序列化为数据 → setData 传给视图层 → 视图层用数据填充 base.wxml 中的对应模板 → 渲染出最终 UI。

2.3 数据驱动渲染的细节：setData 的数据存在哪里？

这是一个常见误区。setData 传递的数据不是文件，而是运行时内存中的 JavaScript 对象：

  • 逻辑层内存：调用 setData 时，数据对象被创建在逻辑进程的堆内存中。
  • 视图层内存：数据通过 Native 桥接传到渲染层（WebView），同样以 JS 对象形式存在内存中。

打包后的文件里只有“指令”，没有“具体数值”。例如打包后的 index.js 包含的是 t.setData({ userInfo: e.data })，而 e.data 具体是“张三”还是“李四”，取决于运行时接口返回，不由打包产物决定。初始静态数据（如 state = { count: 0 }）会作为字面量打包进 JS，但一旦被 setData 修改，新值只存在于内存。

2.4 模板匹配机制：如何知道用 base.wxml 里的哪个模板？

核心是靠数据中的 nn（NodeName） 字段。

  1. Taro 将 VNode 树序列化为包含 nn（节点名）、cl（className）、cn（子节点数组）等字段的 JSON 数据。
  2. 该数据通过 setData 传到视图层。
  3. 视图层根据 nn 值动态拼接模板名：'tmpl_0_' + i.nn（如 tmpl_0_View），从而在 base.wxml 中选择对应的模板。
  4. 通过递归渲染机制（父模板调用子模板）构建完整的 UI 树。

对于不支持模板递归的微信小程序，Taro 会静态生成多套不同层级的模板（如 tmpl_1_View、tmpl_2_View……）来支持到固定深度（默认 16 层）的嵌套。

2.5 VNode 的来源：由框架生成，Taro 负责消费

VNode（虚拟 DOM 节点）由 React 或 Vue 等前端框架在运行时生成，Taro 本身不生产 VNode，而是作为“消费者”进行后续处理。

这个分工明确了各方的职责：

角色 负责工作 产出
React / Vue 执行 createElement 或 h 函数，生成 VNode 树 VNode（框架运行时产物）
Taro 3 通过渲染适配器捕获 VNode 树，将其序列化为 Taro 的模拟 DOM 数据，再通过 setData 传递 setData 所需的 JSON 数据
小程序视图层 接收数据，填充 base.wxml 模板，渲染最终 UI 用户看到的界面

为什么这是 Taro 3 支持多框架的“杀手锏”？

所有现代前端框架（React、Vue、Preact、SolidJS）在运行时的最终产物都是 VNode 树。Taro 3 不关心 VNode 来自哪个框架，只要能够捕获到这棵树，就能完成后续的渲染流程。这就是 Taro 3 能同时支持多套 DSL 的根本原因。

作为对比，Taro 1/2 采用编译时方案，必须在编译阶段就理解代码含义，因此只能深度绑定 React 的 JSX 语法，无法低成本扩展至 Vue 等其他框架。

三、Taro 3 → Taro 4：在“重运行时”基础上的全面进化

Taro 4 并非重构，而是在 Taro 3 架构上的稳健升级，核心变化如下：

特性维度 Taro 3.x Taro 4.x
核心架构 重运行时 延续重运行时，性能增强
编译系统 Webpack 4 + Babel Webpack 5 + SWC（Rust 编写）
构建工具 Webpack Webpack + Vite 双引擎
Node.js 版本 >= 12 >= 18
小程序性能 全运行时渲染 新增 CompileMode（编译时优化）
鸿蒙（HarmonyOS） ❌ 不支持 ✅ 官方支持
包体积 & 速度 基线 包体积减少 30%，编译速度提升 40%
新框架支持 React / Vue 新增支持 SolidJS

3.1 编译与构建：SWC 带来质的飞跃

  • SWC 替换 Babel：冷启动时间减少 65%，增量编译提速 3-5 倍，内存占用降低 40%。
  • 双构建工具：H5 端优先推荐 Vite（开发体验飞跃），小程序端仍以 Webpack 5 为主（持久化缓存、更好的 Tree Shaking）。

3.2 性能优化：CompileMode 弥补运行时短板

Taro 3 的长列表渲染存在性能瓶颈。Taro 4 引入的 CompileMode 允许开发者对特定组件标记，使其在编译时转换为更高效的原生小程序写法，减少运行时开销。在京东商品长列表场景中，开启后首屏渲染性能提升约 30%。

3.3 平台支持：正式拥抱鸿蒙

  • 通过插件 @tarojs/plugin-platform-harmony-ets 即可用 React/Vue 开发鸿蒙应用。
  • 代码复用率可达 85%-92%，适配鸿蒙端仅需额外 10%-15% 的工作量。

3.4 其他重要升级

  • SolidJS 支持：进一步拓宽 DSL 生态。
  • React Native 升级：适配 RN 0.73。
  • TypeScript 覆盖率：达到 95%+。

四、版本选择指南

版本 适合场景 核心理由
Taro 1/2 对性能有极致要求的老项目维护，且使用 React 技术栈 运行时开销最小，接近原生性能
Taro 3 追求开发效率和生态丰富度的新项目 开发体验接近 Web，支持 Vue，可引入海量 Web UI 库
Taro 4 需要鸿蒙支持、追求更快编译速度的新项目，或具备升级条件的 Taro 3 项目 编译速度大幅提升，性能优化手段更丰富，生态更广

升级提醒：从 Taro 3 迁移到 Taro 4 需注意 Node.js 版本（v18+）和 Webpack 相关 Breaking Changes，建议参考官方迁移指南。
