Cookie 三大核心安全设置

Cookie 三大核心安全设置

一、概述

Cookie 是浏览器存储会话状态的重要机制，但也是攻击者的重点目标。
通过设置安全属性，可以防止 Cookie 被窃取、篡改或跨站滥用。

核心安全属性有三个：

  • HttpOnly：防 XSS 窃取
  • Secure：防明文传输窃听
  • SameSite：防 CSRF 跨站携带

二、三大安全属性详解

1. HttpOnly

项目 说明

原理 浏览器仍自动携带，但 JS 无法访问
设置 只能由服务器通过Set-Cookie 设置
防什么 XSS 窃取会话 Cookie
不防 CSRF、XSS 发请求

3. SameSite

项目 说明
作用 控制跨站请求是否发送 Cookie
设置 服务器或前端均可设置，安全场景应由服务器设置
防什么 CSRF 跨站携带 Cookie
不防 XSS

三个取值：

取值 行为 适用场景
Strict 完全禁止跨站发送 Cookie 高安全要求，但影响体验
Lax 允许顶级导航的 GET 请求发送，阻止跨站 POST、AJAX、iframe 默认值，防大部分 CSRF
None 允许跨站发送，必须配合Secure 第三方 Cookie、跨域携带凭证

三、设置主体：服务器 vs 前端

属性 服务器可设 前端 JS 可设 说明
HttpOnly ✅ ❌ JS 无法设置，也无法读取
Secure ✅ ✅ 但安全 Cookie 应由服务器设置
SameSite ✅ ✅ 但安全 Cookie 应由服务器设置

核心原则：

  • 敏感 Cookie（如会话 ID）必须由服务器通过 Set-Cookie 下发。
  • 前端 document.cookie 只应用于非敏感偏好设置。
  • HttpOnly 只能服务器设置，这是其安全意义的根本。

四、属性冲突与覆盖问题

浏览器识别 Cookie 的唯一标识是 Name + Domain + Path。
同名、同 Domain、同 Path 的 Cookie 会被后者覆盖。

1. 安全降级风险

如果前端设置同名 Cookie，会覆盖服务器设置的 Cookie，并丢失安全属性：

  • 丢失 HttpOnly：前端无法设置 HttpOnly，覆盖后新 Cookie 不再受保护，XSS 可窃取。
  • 丢失 Secure：前端忘记加 Secure，Cookie 可能通过 HTTP 明文发送。
  • 放宽 SameSite：攻击者可能将 Strict 覆盖为 None，绕过 CSRF 防护。

2. 功能性问题

  • 跨站请求失败：服务器设 SameSite=Lax，但前端需要跨站携带，导致认证失败。
  • Secure 与 SameSite=None 冲突：缺少 Secure 会被浏览器拒绝。
  • 无法覆盖 HttpOnly Cookie：前端对 HttpOnly Cookie 的写入尝试会被忽略或创建独立 Cookie，导致混乱。

3. 最佳实践

  • 服务器统一管理敏感 Cookie，前端只读不写。
  • 始终使用完整安全属性：
  • 使用 Cookie 前缀强化安全：
    • __Host-：强制 Secure、Path=/、无 Domain
    • __Secure-：强制 Secure

五、攻击者利用前端修改 Cookie 的可能性

前提：存在 XSS 且目标 Cookie 不是 HttpOnly。

1. 能做什么

  • 读取非 HttpOnly Cookie 的值。
  • 用同名、同 Path、同 Domain 的新 Cookie 覆盖它。
  • 修改安全属性：
    • 去掉 Secure → 可能明文传输。
    • 将 SameSite=Strict 改为 None → 允许跨站携带，绕过 CSRF 防护。
    • 设置长期有效的 Cookie，持久化控制。

2. 不能做什么

  • 无法读取或覆盖带 HttpOnly 的 Cookie。
  • 无法设置 HttpOnly 属性。

3. 防御措施

  • 敏感 Cookie 必须设 HttpOnly（最核心）。
  • 服务器统一设置 Secure、SameSite。
  • 全面防 XSS：输出编码、CSP、Trusted Types、DOMPurify。
  • 使用 __Host- / __Secure- 前缀。

跨域携带凭证时：

  • 前端：fetch(url, { credentials: 'include' })
  • 后端 CORS：Access-Control-Allow-Credentials: true，Access-Control-Allow-Origin 为具体源
  • Cookie：SameSite=None; Secure
  • 同时配合 CSRF Token，因为跨站携带 Cookie 会带来 CSRF 风险。

七、总结

Cookie 有三个核心安全属性：HttpOnly 禁止 JS 读取，防 XSS 窃取；Secure 只允许 HTTPS 发送，防明文窃听；SameSite 控制跨站携带，防 CSRF。
它们主要由服务器通过 Set-Cookie 设置，其中 HttpOnly 只能服务器设置。前端可以通过 document.cookie 设置 Secure 和 SameSite，但敏感 Cookie 应由服务器统一管理。
如果前端设置同名 Cookie，会覆盖服务器设置的 Cookie，可能导致安全属性丢失，形成安全降级。
攻击者只有在 XSS 且 Cookie 非 HttpOnly 时，才能通过前端修改 Cookie 的安全属性。防御核心是：敏感 Cookie 必须带 HttpOnly; Secure; SameSite，并做好 XSS 防护。
推荐配置：HttpOnly; Secure; SameSite=Lax。跨域时用 SameSite=None; Secure 并配合 CSRF Token。
