MobX 6 三兄弟：observable、makeAutoObservable、makeObservable

MobX 6 三兄弟：observable / makeAutoObservable / makeObservable

MobX 6.13.6（NODE_ENV=development，Node 20.18.1）。

一、先看结论

在”字段 + getter + 方法”的常规 store 模式下，三者行为几乎完全等价。真正有差异的是这几个角落：

能力 observable makeAutoObservable makeObservable
返回新引用 ✅ Proxy 副本 ❌ 原地改 ❌ 原地改
默认递归 ✅ deep ✅ deep 由你选
动态加字段 ✅响应式 ❌ ❌
this 绑定（解构后调用） ❌ ❌（需显式autoBind） ❌（需action.bound）
逐字段 deep/ref/shallow ✅第二参数 ⚙️ overrides ✅ 注解
支持继承 — ❌ 抛 Error ✅
精细注解成员 ✅ 注解参数 ⚙️ overrides ✅

意外发现：observable.length === 3——它支持第二参数传注解，可以逐字段控制 deep/ref/shallow。这一点打破了我最初的假设（”observable 只能 deep”）。

二、逐个 API 的行为

observable(source, options?, annotations?)

  • 返回 Proxy 副本，不修改原对象（实测：observable(r1) === r1 → false）
  • 默认 deep，递归处理所有嵌套
  • 支持动态加字段，且真响应式（实测：autorun 真的触发）
  • 支持第二参数逐字段注解
  • 方法会被自动标为 action，getter 会被自动标为 computed

makeAutoObservable(target, overrides?, options?)

  • 原地修改，返回同一个引用（实测：makeAutoObservable(r2) === r2 → true）
  • 自动推断：字段 → observable，getter → computed，方法 → action
  • 默认 deep（实测：深层 user.profile.name 是 observable）
  • 默认不绑定 this（实测：解构后调用报错）
  • 不能用于带 super 的子类（实测：抛 Error: [MobX] 'makeAutoObservable' can only be used for classes that don't have a superclass）
  • 可用 overrides 改个别字段的深度（实测：overrides: { user: observable.ref } 生效）

makeObservable(target, annotations)

  • 原地修改，返回同一个引用
  • 递归深度由你决定（deep / ref / shallow 混用）
  • 支持继承
  • 每个成员的行为完全可控

四、选型建议

场景 推荐
通用 store（类 / 对象字面量） makeAutoObservable
有继承结构 makeObservable
逐字段 deep/ref/shallow 混用 makeObservable 或 observable(源, 注解)
动态键控字典 / Map / Set observable
纯数据对象变响应式 observable
需要this 解构后调用 显式{ autoBind: true } 或 action.bound

日常 store 用 makeAutoObservable；继承或要极致控制用 makeObservable；动态键控和纯数据用 observable。

五、踩坑指南

坑 1：autoBind 默认不生效

实测确认：makeAutoObservable(this) 后解构调用方法，this 丢失。

规避：

坑 2：observable 返回副本，原引用看不到变化

规避：要原地改就用 makeAutoObservable，或确保没有外部引用原对象。

坑 3：makeAutoObservable 不支持继承

实测确认：带 super 的子类直接抛 Error。

规避：继承场景一律用 makeObservable。

坑 4：动态加字段不响应

makeAutoObservable / makeObservable 加的新字段不是 observable。

规避：预声明所有字段，或换成 observable({...})。

坑 5：enforceActions 违规只 warn 不抛错

实测确认：try/catch 捕不到 enforceActions 违规。

规避：盯着控制台 warn 面板，别指望异常打断程序。

坑 6：生产构建没有检查

MobX 的 enforceActions 检查在 production 构建里被剥离。本地 / CI 没警告 ≠ 代码合规。

规避：在 development 构建里验证代码规范。

坑 7：instanceof Proxy 是无效检测

Proxy 不是普通构造函数，没有 prototype。

规避：想判断是不是 Proxy，读源码或看行为，不要用 instanceof。

六、this 绑定的正确心智模型

实测汇总：

写法 解构后调用
observable({...}) 的方法 ❌
makeAutoObservable(对象/class) 默认 ❌
makeAutoObservable(..., { autoBind: true }) ✅
makeObservable(this, { inc: action.bound }) ✅
箭头函数 / 手动.bind(this) ✅

最省心的规避：不写 onClick={store.inc}，写 onClick={() => store.inc()}。比配 autoBind 更直接。

七、this 绑定：一条被广泛误传的结论

很多资料说：

“makeAutoObservable 默认 autoBind: true，自动把方法绑到实例上。”

6.13.6 实测：不成立。

要么 autoBind 的默认值不是 true，要么它的生效条件和直觉不符。以实测为准——写代码时显式传 { autoBind: true }。
