SSE 服务器发送事件

SSE 是什么

SSE（Server-Sent Events，服务器发送事件）是一种基于 HTTP 协议的技术，允许服务器通过单条持久连接向客户端单向推送实时数据。它的客户端 API 由 EventSource 接口提供，自 2020 年 1 月起已在所有主流浏览器中广泛可用。

从通信模型上看，SSE 建立的是单向通道：只有服务器可以向客户端发送数据，客户端无法通过这条连接向服务器回传信息。这与 WebSocket 的双向全双工通信有本质区别。

SSE 在工程实现上非常轻量。服务器只需将响应头设置为 Content-Type: text/event-stream，然后持续向该连接写入符合特定格式的文本数据即可。客户端通过 new EventSource(url) 建立连接后，监听 message 事件或自定义事件来接收数据。

SSE 的数据格式是纯文本，以 UTF-8 编码。每条消息由若干字段行组成，常用的字段包括：data（消息内容）、event（事件类型）、id（事件 ID，用于断线续传）、retry（重连间隔）。消息之间以两个换行符分隔。

SSE 特点

原生自动重连是 SSE 最实用的特性之一。如果连接意外断开，浏览器会自动尝试重新建立连接，默认间隔约为 3 秒，服务器也可以通过 retry 字段控制这个间隔。配合 id 字段，客户端在重连时会携带 Last-Event-ID，服务器可以据此从断点处恢复推送。

基于标准 HTTP，SSE 天然兼容现有的基础设施。不需要协议升级、不需要特殊的服务器软件，Nginx、CDN、负载均衡器等对 HTTP 的支持可以直接复用。鉴权方面也可以直接使用 Cookie 或标准的 HTTP 头。

实现成本低。客户端只需几行代码，服务端也只需要设置正确的响应头并持续写入文本流。相比之下，WebSocket 需要处理握手升级、心跳保活、自定义协议帧等额外复杂度。

但 SSE 有明确的限制。它只支持服务器到客户端的单向推送，且数据只能是 UTF-8 文本，无法直接传输二进制数据。最需要注意的限制是：在非 HTTP/2 环境下，浏览器对同一域名的 SSE 连接数限制为 6 个。这意味着用户打开多个标签页时，很容易耗尽连接配额。这个问题在 Chrome 和 Firefox 中被标记为“不会修复”。启用 HTTP/2 后，上限提升至约 100 个，可以基本消除该困扰。

与 WebSocket 对比

两者的核心差异在于通信方向和适用场景。

维度 SSE WebSocket
通信方向 单向（服务器→客户端） 双向全双工
协议基础 标准 HTTP 需 HTTP 升级握手，自定义帧协议
数据格式 UTF-8 文本 文本 + 二进制
自动重连 浏览器原生支持 需应用层手动实现
连接数限制 非 HTTP/2 下每域名 6 个 无此限制
服务端复杂度 低，普通 HTTP 服务即可 需专用 WebSocket 库或网关

SSE 的典型适用场景是只需要服务器推送的场景：实时通知、股票行情、新闻流、日志推送、AI 流式回复等。ChatGPT 的逐字输出效果就是基于 SSE 实现的。WebSocket 则适合需要双向交互的场景，如在线聊天、协同编辑、多人游戏。

选型建议很简单：如果数据流只需要从服务器流向客户端，优先考虑 SSE，因为实现更简单、运维成本更低；如果需要客户端频繁向服务器发送消息，或者需要传输二进制数据，则必须使用 WebSocket。

客户端：Fetch 手动实现

当需要 POST、自定义头或更细粒度的控制时，可以用 fetch 读取流式响应并手动解析 SSE 格式。

核心是读取 response.body，用 TextDecoder 解码，按 \n\n 切分事件，再提取 data: 等字段。

不想手动解析也可以使用解析库：eventsource-parser。
