从零构建企业级 RAG 知识库

从零构建企业级 RAG 知识库：NestJS + React + pgvector 全栈实战

一、为什么要写这个项目

RAG（Retrieval-Augmented Generation） 在 2024 年被吹上了天，2025 年又被骂成”过时方案”。但企业内部知识库问答、客服话术检索、合同条款比对这些场景，RAG 依然是性价比最高的方案——不需要训练模型，只要做好切片、检索、引用三件事。

市面上的开源 RAG 框架（Dify、FastGPT、MaxKB）功能越来越重，但当你想接入自己的百炼 API、自定义切片策略、或者给前端加一个 3 步骤上传向导时，二次开发的成本可能比自己搭一套还高。

所以我决定用最小可维护的技术栈，从零实现一个 MVP 级别但生产可用 的 RAG 系统。本文是这个项目的完整复盘。

二、技术选型：为什么选这些

层 选型 理由
构建 pnpm + Turborepo 真正的 workspace，shared 包类型实时同步
后端 NestJS 9 + TypeORM 模块化清晰，SSE/Guard/Interceptor 都是内置的
数据库 PostgreSQL 17 + pgvector 一个库搞定结构化数据 + 向量 + 全文检索，运维零成本
Embedding/LLM 百炼 qwen3.7-text-embedding + qwen3.7-plus 1024 维向量，128K 上下文，OpenAI 兼容接口
前端 React 19 + Vite + Zustand + shadcn 轻量、类型安全、Tailwind v4 零配置

没有选 LangChain JS 做全套。只用了它的 RecursiveCharacterTextSplitter 做文本分段，其他全部手写。LangChain 的抽象层太厚，debug 困难，很多时候你要的只是”按分隔符切段”，而不是一个 500 行的 Chain。

五、核心实现二：混合检索（Dense + Sparse）

只有向量检索为什么不够？

向量相似度擅长”语义相近”（”销售额环比” 和 “销量变化趋势” 能对上），但遇到精确匹配查询（”XS20250103001 这个单号”）时，纯余弦相似度可能会把正确结果排在后面。

解决方案：pgvector 余弦距离 + PostgreSQL tsquery 全文检索，加权融合

踩过的坑：最初没做 min-max normalize，向量分数在 0.5+，关键词 rank 只有 0.06，融合后全被向量盖住。加了归一化之后才正常。

Rerank 集成用的是百炼的 qwen3-rerank，放在融合之后做二次排序。开启后检索质量明显提升，尤其是精确匹配场景。

六、核心实现三：SSE 流式问答

用户发消息 → 后端检索 Top-K 切片 → 拼 Prompt → 调 LLM → SSE 流式返回。

停止生成：前端用 AbortController，点停止后 abort() 断开 SSE 连接。后端 catch 到错误就停。前端检测到流断了但有 content，显示”已停止”。

七、核心实现四：知识库隔离

项目支持多个知识库，每个知识库下有独立的文档、切片、检索历史。
隔离方式很简单：所有 API 都接收 knowledgeBaseId 作为第一个 query 参数，后端用 innerJoin 保证切片只能查到自己知识库的：

八、核心实现五：3 步骤上传向导

原来设计的上传是一个弹窗，点击上传按钮就加文件进去直接切片。现在改成独立页面，引导用户做更精细的配置：

步骤 1：选类型 + 上传

  • 两卡片单选：文本格式 / 表格格式
  • 根据选的类型，显示不同的上传区域
  • 上传后隐藏上传区域，显示文件卡片（文件名 + 大小 + 垃圾桶删除）
  • 切换类型时自动清空已上传文件

步骤 2：文件处理配置

  • 文本 → 自动分段（默认）/ 自定义（选分隔符如中文句号、英文问号、换行，设 chunkSize、chunkOverlap）
  • 表格 → 选表头是第几行、数据从第几行开始解析

步骤 3：自动切片 + 进度

  • 提交后后台轮询文档状态，每 2 秒查一次
  • 状态变成 completed 后跳回文档管理页并刷新

前端 Wizard 用 Zustand 一个 state 对象管理 3 步的所有状态，buildConfig() 在提交时把 UI 状态转成后端类型。

九、踩过的 5 个坑

1. pgvector 索引类型选错

2. TypeORM synchronize 自动迁移 jsonb 列
Entity 上加了 @Column({ type: 'jsonb', nullable: true }) config 后，TypeORM 会 ALTER TABLE ADD COLUMN config jsonb——但需要 API 重启才生效。我一开始手动写 SQL 加列，结果忘了 TypeORM 自己也在管 schema。

3. Excel __EMPTY 表头
合并单元格后 sheet_to_json 会产生 __EMPTY 列名。必须过滤：Object.keys(row).filter(k => !k.startsWith('__EMPTY'))。

4. SSE 被 Nginx 缓冲
流式内容攒 64KB 才发，前端等几秒才有反应。必须加 X-Accel-Buffering: no header。

5. LangChain TextSplitter 的 chunkOverlap 是字符数，不是百分比

十、后续规划

MVP 完成了，但离生产还有不少差距。按优先级排：

  1. 检索评估：整理小型测试集（20 个查询 + 预期文档），跑 top-k 命中率，找到 denseWeight 最佳值
  2. 会话历史：新增 chat_sessions / chat_messages 表，多轮对话时带上下文一起调 LLM
  3. 引用来源可点击：SourcesPanel 点击某条引用 → ChunkManage 自动定位并高亮对应切片
  4. 用户权限：登录 + 知识库级 ACL
  5. 生产部署：HTTPS + 定时 pg_dump + 对象存储存文件

十一、结语

这个项目证明了一件事：企业级 RAG 不需要 Dify 那么重。NestJS + React + pgvector 三样东西，各自负责自己的事，加起来就是一个能跑、能调、能改的知识库系统。

最有成就感的时刻不是”上传一个文档然后检索到结果”，而是：用户问出”XS20250103001 这个销售单的销售员是谁？”，系统从 5000 个切片里精准找出那一行 Excel 数据，Rerank 把它压到第 1 位，然后 LLM 回答”销售员是张三，销售门店深圳南山店”——全程 300ms。

切片对了、检索准了、答案自然就对了。这才是 RAG 的本质。
