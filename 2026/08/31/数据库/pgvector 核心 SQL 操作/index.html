pgvector 核心 SQL 操作

1. 概述

  • pgvector 是 PostgreSQL 的扩展，在标准 SQL 中引入 vector 数据类型，支持向量相似度搜索。
  • 优点：无需引入新数据库，复用 PG 的事务、备份、安全机制，适合中小规模向量检索（百万~千万级）。

2. 安装与启用

注：PG 16+ 官方镜像已内置，自建需通过 apt 或源码安装。

3. 表结构与向量列

  • 使用 vector(n) 类型，n 必须与嵌入模型输出的维度一致（如 OpenAI ada-002 为 1536）。

可以一张表建多个向量列（不同模型或不同字段）。

5. 相似性搜索（核心） 📌（本节已扩充操作符详解）

距离操作符一览

操作符 距离类型 数学公式 适用场景
<-> 欧几里得 (L2) (\sqrt{\sum{(A_i - B_i)^2}}) 图像/音频特征（模长重要时）
<=> 余弦距离 (1 - \frac{A \cdot B}{|A||B|}) 文本嵌入首选（关注方向）
<#> 负内积 (- (A \cdot B)) 推荐系统精排（模长大者占优）
<+> 曼哈顿 (L1) (\sum{|A_i - B_i|}) 稀疏向量 / 存在离群值场景

📌 核心区别：关注”方向”还是”大小”？

  • 余弦距离 (<=>)：只关注方向，忽略模长。即使向量 B 是 A 的 10 倍长，只要方向一致，距离为 0。→ 文本语义搜索首选。
  • 欧几里得 (<->)：同时关注方向和大小。模长差异会直接拉大距离。→ 适合图像亮度、音频能量等”强度”有意义的场景。
  • 负内积 (<#>)：同时放大方向和大小。模长越大的向量越容易”赢”。→ 热门物品在推荐中自然获得加成。
  • 曼哈顿 (<+>)：对异常值不敏感。个别维度的巨大差异不会被平方放大。→ 高维稀疏特征或噪声较多的数据。

📌 避坑指南（重要！）

操作符 是否隐式归一化 最大陷阱
<=> ✅ 是 如果业务依赖”强度”，它会混淆强弱文档
<-> ❌ 否 高维空间中所有点距离可能趋同（维度灾难）
<#> ❌ 否 结果受模长主导，非推荐场景慎用
<+> ❌ 否 在密集向量中表现通常不如欧氏

📌 实战选择决策链

  1. 文本/语义嵌入 → 直接用 <=>（90% 场景够用）
  2. 图像/音频特征 → 优先 <->
  3. 推荐系统排序 → 可尝试 <#>（注意向量已归一化时，<=> 和 <#> 等价）
  4. 稀疏向量或离群值多 → 考虑 <+>

特别提醒：OpenAI 等主流嵌入模型输出的向量通常已归一化（模长为 1）。此时 <=>（余弦）和 <#>（负内积）在排序结果上完全等价，但 <#> 计算略快。不过为了可读性，生产环境仍普遍推荐 <=>。

6. 索引加速（性能关键）

  • 数据量 > 1万行时强烈建议建索引。
  • 索引类型：
    • HNSW（推荐）：查询快、召回高、无需预训练，适合大部分场景。
    • IVFFlat：构建更快，但需表中已有数据，且查询速度通常慢于 HNSW。

7. 实用建议 & 注意事项（📌 已补充索引匹配规则）

  • 索引操作符必须与查询操作符匹配：若查询用 <=>（余弦），索引必须用 vector_cosine_ops；若用 <->（L2），则用 vector_l2_ops。否则索引不会被使用，导致全表扫描。
  • 向量维度固定：一旦表创建，vector(n) 的 n 不可更改，必须重建表。
  • 索引占用空间较大，需提前评估存储（HNSW 索引约占原始数据的 1.5~2 倍空间）。
  • 批量插入前建议先建索引，或者插入完成后再建（后者可能更高效，但需权衡建索引期间的服务可用性）。
  • 关于 CONCURRENTLY：虽然可以避免锁表，但会消耗额外 IO 和 CPU，且建索引时间会更长，需在业务低峰期执行。

8. 常用速查

操作 命令
启用扩展 CREATE EXTENSION vector;
建表（含向量列） CREATE TABLE t (v vector(384));
插入向量 INSERT INTO t VALUES ('[0.1, 0.2]'::vector);
余弦相似搜索（Top 5） SELECT * FROM t ORDER BY v <=> '[0.1,0.2]'::vector LIMIT 5;
建 HNSW 索引（余弦） CREATE INDEX ON t USING hnsw (v vector_cosine_ops);
建 HNSW 索引（欧氏） CREATE INDEX ON t USING hnsw (v vector_l2_ops);
