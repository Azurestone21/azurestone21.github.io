React + Jest 前端项目单元测试

适用项目：Taro + React + Webpack（小程序 / H5）

一、安装 Jest 相关依赖

依赖 作用
jest 测试运行器本身。负责发现测试文件、执行用例、提供断言（expect）和 Mock 能力（jest.fn()、jest.mock()），内置快照测试。是整个测试流程的调度中心。
jsdom 底层的 DOM 模拟实现，用 JavaScript 模拟浏览器的大部分 DOM API。
jest-environment-jsdom Jest 的测试环境适配器。Jest 默认跑在 Node 环境，没有 window、document；这个包让测试在 jsdom 提供的模拟浏览器环境中执行，React 组件才能正常渲染。
@testing-library/react React 测试工具库。提供 render、screen、fireEvent 等 API，用于渲染组件、查询 DOM、模拟交互。设计理念是鼓励测试用户可感知的行为，而非组件内部实现，降低重构误报。
@testing-library/jest-dom 扩展 Jest 断言匹配器。提供 toBeInTheDocument()、toBeVisible()、toBeChecked() 等语义化 DOM 断言，失败信息更易读。
@testing-library/user-event 比 fireEvent 更贴近真实用户操作的交互模拟库，推荐用于点击、输入等场景。
ts-jest Jest 的 TypeScript 转换器。在测试运行时把 .ts/.tsx 编译成 JavaScript，让 Jest 能执行。
@types/jest Jest 的 TypeScript 类型定义。
@types/jsdom jsdom 的 TypeScript 类型定义。

版本提示：ts-jest 的主版本通常跟随 Jest 主版本。版本不匹配时优先排查这一对组合。

二、配置 Jest

创建 jest.config.js：

2.1 顶层配置

testEnvironment: 'jsdom'
测试在 jsdom 模拟的浏览器环境里跑，提供 window、document 等 DOM API。React 组件测试必需。

testMatch: ['<rootDir>/src/**/_.test.{ts,tsx}']
只把 src下匹配_.test.ts/\*.test.tsx 的文件当测试。**tests**目录里不叫.test. 的文件不会被识别。

2.2 路径与资源映射：moduleNameMapper

'^@/(.*)$' 和 '^~/(.*)$'
对应项目 Webpack 配置的路径别名。Jest 不走 Webpack，必须在这里重新声明一遍。

'\\.(css|scss|less|sass)$'
样式文件映射到 __mocks__/styleMock.js（通常导出空对象）。Jest 不能解析 CSS，用空模块替代，避免 import 样式时报错。

'\\.(png|jpg|jpeg|gif|svg|ico|webp)$'
图片资源映射到 fileMock.js（通常导出文件名字符串）。Jest 不处理二进制资源。

__mocks__ 目录
Jest 约定的手动 Mock 目录，用来存放模块替身，让 Jest 在测试时自动或按需替换真实模块。详见第四节。

2.3 TypeScript 转换：transform

'^.+\\.tsx?$': ['ts-jest', { tsconfig: 'tsconfig.json', diagnostics: false }]
所有 .ts/.tsx 文件交给 ts-jest 转换，使用项目根目录的 tsconfig.json。

diagnostics: false：关闭 ts-jest 的类型检查。好处是测试能先跑起来、速度更快；代价是类型错误不会在测试阶段暴露，需要靠 tsc --noEmit 或 IDE 单独把关。建议保持 false，因为测试运行时被类型错误阻断（如“参数数量不对”）会掩盖真正的行为问题，而类型检查应交给独立流程。

2.4 覆盖率统计：collectCoverageFrom

只统计 src/shared 和 src/pages 下的文件覆盖率，排除类型声明文件。只在加 --coverage 时生效，且只影响“统计哪些文件”，不影响“跑哪些测试”。

2.5 测试超时：testTimeout

单个测试超时 10 秒（默认 5 秒）。异步测试、带定时器的测试可以放宽到这个值。

2.6 初始化测试环境：setupFilesAfterEnv

在每个测试环境初始化后执行 setupTests.ts。这里可以配置全局 Mock、断言扩展等，让所有测试用例共用。

三、Taro 项目的特殊处理

Taro 项目的测试比纯 Web React 多一层复杂度：@tarojs/taro、@tarojs/runtime 是 ESM 模块，Jest 默认不转译 node_modules，直接 import 会报 Must use import to load ES Module。推荐方案是 Mock 掉 Taro，而不是让 Jest 转译它。

这一行不带工厂函数，只是告诉 Jest“去 __mocks__ 找替身”，不会覆盖 Mock 文件导出的内容。

3.3 Mock 的 API 要按需补全

Mock 对象里只声明了实际用到的 API。如果被测代码调用了 Taro.navigateTo 而 Mock 里没有，会得到 undefined 并报错。按项目实际用到的 API 补全即可。

3.4 不推荐：转译 Taro 包

在 jest.config.js 中加 transformIgnorePatterns: ['node_modules/(?!(@tarojs)/)'] 可以让 Jest 转译 Taro，但：

  • Taro 4.x 的 ESM 结构在 pnpm 的嵌套目录下，负向断言正则容易匹配不到真实路径；
  • 转译 Taro 运行时速度慢，且可能引入新的兼容问题；
  • 对一个只测工具函数和组件行为的项目来说，不值得。

结论：Mock 掉 Taro 是最省事、最稳定的方案。

四、__mocks__ 目录使用说明

4.1 两种放置位置

位置 用途 是否自动生效
项目根目录 __mocks__/（与 node_modules 同级） Mock 第三方包（@tarojs/taro、axios） 多数配置下仍需测试文件里 jest.mock('包名') 触发
被测文件同目录 __mocks__/ Mock 项目内部模块（相对路径 import） 不自动，必须显式 jest.mock('../utils/format')

4.2 项目里 __mocks__ 的两种用法

（1）Jest 约定的手动 Mock：如 __mocks__/@tarojs/taro.js，靠 jest.mock('@tarojs/taro') 触发。

（2）moduleNameMapper 映射的资源替身：如 styleMock.js、fileMock.js。这两个文件只是自定义的目录名，靠 moduleNameMapper 显式映射生效，和 Jest 的自动 Mock 机制无关。放哪、叫什么名字都可以，项目惯例叫 __mocks__。
