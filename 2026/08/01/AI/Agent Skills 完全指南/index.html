Skills的结构

Agent Skills 完全指南：从原理到实践

引言：Agent 能力扩展的第三条路

2025 年 10 月，Anthropic 正式发布 Agent Skills，并将其定位为“AI Agent 生态的核心能力扩展机制”。在此之前，给 Agent 注入领域知识主要有两条路径：一是把所有指令写进 System Prompt，二是在运行时拼接上下文。两条路都有各自的瓶颈——前者让上下文迅速膨胀，后者缺乏结构化和可复用性。

Agent Skills 给出了第三条路：把领域知识打包成文件系统上的标准化文件夹，让 Agent 按需发现、按需加载。Anthropic 在官方工程博客中给出了一个精准的类比——“为一个 Agent 构建 Skill，就像为新员工准备一份入职指南”。你不需要为每个场景重新训练一个专用 Agent，只需要把程序性知识封装成可组合、可共享的 Skill，就能让通用 Agent 在需要时化身为特定领域的专家。

Skills 发布后迅速被多个平台采纳。Microsoft Learn 将其定义为“可移植的指令、脚本和资源包，为 Agent 提供专门功能和领域知识”。Agent Skills 也已成为一个开放标准，规范文档托管在 agentskills.io，目标是实现跨平台的可移植性。

什么是 Agent Skills

Agent Skills 是模块化的能力扩展包，专为通用 AI Agent 设计，用于注入流程化、确定性的领域知识。它的本质是一个基于文件系统的、可复用的知识包，让通用 Agent 在相关任务上按需加载成领域专家，而不是把整本操作手册塞进每一次对话的系统提示词。

一个 Skill 解决的核心问题是程序性知识的复用。它不是“这次怎么做”的一次性指令，而是“这类事以后都这么做”的标准化操作流程（SOP）。Skill 封装的是“何时用、怎么做”的知识——包括触发条件、执行步骤、边界判断、禁止行为和输出验证。

从技术本质上看，Skill 是有组织的指令、脚本和资源文件夹，Agent 可以动态发现并加载它们以在特定任务上表现更好。它既可以简单到一个 SKILL.md 文件，也可以复杂到包含脚本、参考文档和资源模板的完整目录结构。

基本结构：一个文件夹，三层加载

Agent Skills 的目录结构遵循极简原则。最简单的 Skill 就是一个包含 SKILL.md 文件的文件夹。随着复杂度增加，可以在目录中捆绑额外的资源文件。

SKILL.md 由两部分组成：YAML frontmatter 和 Markdown 正文。Frontmatter 必须用 --- 标记开始和结束，包含以下字段：

字段 必需 约束
name 是 最多 64 字符，仅小写字母、数字和连字符，不可首尾为连字符，需与目录名一致
description 是 最多 1024 字符，非空，需描述“做什么”和“何时使用”
license 否 许可证名称或对捆绑许可证文件的引用
compatibility 否 最多 500 字符，环境要求（产品、系统包、网络访问等）
metadata 否 任意键值对，用于附加元数据
allowed-tools 否 预批准工具列表（实验性）

description 是最关键的字段。它是 Agent 判断是否加载某个 Skill 的主要依据——Agent 在启动时会扫描所有 Skill 的 description，将其与当前任务做语义匹配。官方推荐的写法公式是：做什么 + 何时使用 + 触发短语。一个好的 description 会主动列出用户可能说出的关键词和场景，以对抗 Agent “欠触发”的倾向。

Markdown 正文则是第二级指令，理想情况下应控制在 500 行以内。正文应包含工作流程、资源索引、边界说明和输出模板等内容。官方建议正文使用祈使句式，并解释“为什么”而不只是“做什么”，让 Agent 能适应边缘情况。

如何设计一个高质量的 Skill

设计一个 Skill 的核心判断标准是：任务中是否存在显著的专家判断差异。如果熟手和新手做出来差距很大，这个任务就值得 Skill 化；如果只是简单的执行步骤，封装成本可能并不划算。

对比一个糟糕的例子：description: Helps with PDFs.——没有说明能力边界，也没有给出触发场景。

第二，让 SKILL.md 保持精简。 不要把 SKILL.md 写成百科全书的正文。它应该像一个组织良好的手册的目录页——告诉 Agent“这里有哪几章，什么时候去翻哪一章”，而把详细内容放到 references/ 中。当参考文件超过 300 行时，建议在文件开头添加目录。

第三，用脚本替代重复代码生成。 如果 Skill 涉及确定性或重复性的操作，把可执行代码放到 scripts/ 目录中。执行脚本时，只有脚本的输出结果会进入上下文，代码本身不会，这能显著节省 Token。Anthropic 官方的 skill-creator 和 frontend-design Skill 是展示渐进式披露和脚本自动化最佳实践的优秀范例，值得参考。

第四，为边缘情况做好设计。 高质量的 Skill 需要明确回答：何时触发、何时不触发、按什么流程执行、边界情况怎么判断、禁止哪些行为、输出如何验证、失败后如何修正。这七个问题构成了一个可复用、可验证、可迭代的专家能力包的基本框架。

第五，考虑安全风险。 Skills 并非没有代价。2026 年 2 月的一项审计发现，在 3,984 个 AI Agent Skill 中，36.82% 存在安全缺陷，76 个包含确认的恶意载荷。Snyk 的研究也发现 36% 的 Skill 存在提示注入问题。设计 Skill 时，应避免在文件中硬编码凭据，谨慎处理来自外部的指令，并对脚本权限进行最小化授予。

什么情况下应该使用 Skills

Skills 最自然的适用场景是重复性工作流。Anthropic 官方博客给出的判断标准很直接：“如果你在多个对话中反复输入相同的请求，那就是时候创建一个 Skill 了”。

具体来说，以下三类场景最适合 Skill 化：

组织级工作流。 品牌规范、合规流程、文档模板——这些是团队中每个成员都需要遵循的标准，但每次都要向 AI 重新解释一遍。把这些标准封装成 Skill，Claude 在生成演示文稿或文档时会自动应用，无需每次重复说明。

领域专业知识。 Excel 公式、PDF 操作、数据分析、代码审查——这些需要专家判断的领域，Skill 能把熟手的经验固化为可复用的操作流程。例如，一个代码审查 Skill 可以封装触发条件、审查流程、反模式约束和输出格式规范。

个人偏好与工作方法。 笔记系统、编程模式、研究方法——个人的工作习惯同样值得 Skill 化。这类 Skill 的维护成本低，但能显著提升日常与 Agent 协作的效率。

相反，不适合 Skill 化的场景包括：简单的单步执行（用 Prompt 就够了）、需要运行时动态变化的信息（用 MCP 工具查询更合适）、以及有严格状态机要求的流程控制（Workflow 更合适）。

Skills 如何加载：渐进式披露

Skills 最核心的设计原则是渐进式披露（Progressive Disclosure） 。它借鉴了 UI/UX 领域的信息披露策略，将信息按需分层加载，在上下文效率和知识深度之间取得平衡。

整个加载过程分为三层：

第一层：元数据层（启动时加载）。 Agent 启动时，只将所有已安装 Skill 的 name 和 description 预加载到系统提示中，每个 Skill 大约消耗 100 Token。即使安装了 30 个 Skill，开局消耗也仅约 3000 Token。这层信息的作用是让 Agent 知道“有哪些 Skill 存在，它们大概能做什么”。

第二层：指令层（触发时加载）。 当用户请求与某个 Skill 的 description 语义匹配时，Agent 才会读取完整的 SKILL.md 正文，通常控制在 5000 Token 以内。这层信息告诉 Agent“具体怎么做”。

第三层：资源层（按需加载）。 scripts/、references/ 和 assets/ 中的文件不会自动进入上下文。只有当 SKILL.md 正文中明确指引 Agent 去读取某个文件或执行某个脚本时，Agent 才会主动使用工具去访问它们。读到才进，不读就不进，因此其体积理论上几乎没有上限——“可以捆绑进 Skill 的上下文量实际上是无限的”。

这种三层结构的关键在于物理分离：把“有哪些能力”和“具体怎么做”拆开，让 Agent 在启动时只需要知道目录的存在，而不需要加载每一章的内容。Anthropic 官方的 PDF Skill 是一个典型案例：SKILL.md 核心文件保持精简，表单填写指令被移到独立的 forms.md 中，Agent 只在真正需要填表时才去读取那个文件。

Skills 与 Prompt / Memory / MCP 的区别

理解 Skills 的最佳方式，是把它放在 Agent 能力体系的坐标系中，与相邻概念做清晰对比。

Skills vs Prompt。 Prompt 是“一次性指令”，告诉 AI 这一次要做什么；Skill 是“程序性知识”，教 AI 遇到一类事情时应该怎么做。用做菜来类比：Prompt 是你临时口头交代“今天做个宫保鸡丁”，Skill 是厨师掌握的那套宫保鸡丁标准做法。Skills 不是 Prompt 的替代品，而是Prompt 的容器——一个 Skill 里必然包含精心设计的 Prompt，外加脚本、依赖声明和测试用例。

不能把 Skill 直接写进 System Prompt：几十个 Skill 的全文会让 System Prompt 极度臃肿，token 成本极高，且 System Prompt 是静态的，修改会破坏 prompt cache，无法支持 Skill 的动态更新与演进。

Skills vs Memory。 Memory 保存的是陈述性知识（“用户偏好中文回复”），Skill 保存的是程序性知识（“部署到生产环境的标准流程”）。Memory 在每轮对话中自动注入系统提示，而 Skill 按需加载。两者的边界在于：可复用的操作方法归入 Skill，事实性偏好信息归入 Memory。

Skills vs MCP。 这是最容易混淆的一对概念。MCP 是通信协议，解决“能不能连”——让 AI 标准化地访问外部工具和数据；Skill 是操作手册，解决“会不会做”——教 AI 如何按规范流程完成任务。Anthropic 的官方表述最为精炼：“MCP 把 Claude 连接到数据；Skills 教 Claude 如何用这些数据做事”。MCP 让 AI 能连上数据库，Skill 教 AI 怎么按公司的规范查数据。

维度 Prompt Memory MCP Skill
定位 一次性指令 持久化事实 工具通信协议 标准化能力包
解决 这次做什么 记住什么 能不能连 会不会做
加载 随对话 每轮自动注入 运行时调用 按需渐进加载
生命周期 单次对话 跨会话 持续 持续，可版本管理

常见问题与排查

Skill 不触发怎么办？ 原因几乎总是出在 description 上。Agent 使用语义匹配来判断是否加载 Skill，如果用户请求的语义与 description 的重叠不够，就不会匹配。解决方案是：对照用户实际表达请求的方式检查 description，添加用户会真实说出的触发短语，并用多个变体进行测试。

Skill 不加载怎么办？ 检查结构性要求：SKILL.md 文件必须位于一个命名目录内，文件名必须恰好是 SKILL.md（全部大写），而不是在技能根目录下。使用 claude --debug 查看加载错误。

多个 Skill 冲突怎么办？ 如果 Agent 在多个 Skill 之间感到困惑，说明 description 过于相似，需要让它们更具区分度。如果个人 Skill 被忽略，检查是否存在同名的高优先级 Skill（如企业级 Skill 会覆盖个人级同名 Skill）。

Skill 的上下文会爆炸吗？ 这是对渐进式披露最常见的误解。启动时只加载元数据，触发时加载指令层，资源层按需读取。即使安装了 100 个 Skill，开局消耗也仅约 10,000 Token。真正触发执行的通常只有 1-3 个 Skill，且资源层不会一次性全部进入上下文。

Skills 的安全风险有哪些？ 主要风险包括：脚本执行（Skill 目录中的 .py/.sh/.js 文件）、指令操纵（要求忽略安全规则或隐藏操作的指令）、硬编码凭据（API 密钥、令牌）。企业级部署应考虑沙箱隔离、权限声明和质量审核三层防护。

总结

Agent Skills 的核心贡献不在于“更长的 Prompt”或“更复杂的配置”，而在于它把程序性知识的复用变成了一个标准化的工程问题。通过文件系统的天然结构、渐进式披露的加载机制、以及跨平台的可移植规范，Skills 让通用 Agent 能够在需要时精准地加载所需的领域知识，而不必在每次对话中都背负全部能力的上下文成本。

理解 Skills 的关键，是把它放在 Agent 能力体系的坐标系中：Prompt 管这一次，Memory 管记住什么，MCP 管能不能连，Skill 管会不会做。四者互补而非替代。掌握这个坐标系，比记住任何具体的 SKILL.md 写法都更有价值。
