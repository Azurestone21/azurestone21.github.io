Function Calling

Function Calling 详解：模型如何”说出”要调什么，应用如何”真正”去执行

一、先给定义：Function Calling 到底是什么

用三句话回答：

  1. Function Calling 是一种让大模型输出”结构化工具调用请求”的机制。 模型不再只生成自然语言，而是可以生成一段规定格式的数据：调用哪个工具、传什么参数。
  2. 模型只生成意图，不执行函数。 真正调用 API、查数据库、发邮件的，是应用侧的程序。
  3. 执行结果会回填给模型，模型基于结果继续推理或回答。 所以它是一个”模型决策 → 应用执行 → 结果回填 → 模型再决策”的闭环。

如果只能记一句：

Function Calling = 模型负责”说清要调什么”，应用负责”真正去调”，结果再喂回模型继续想。

用一个场景把它串起来

用户问：”广州今天天气怎么样？”

没有 Function Calling 时，模型只能回答”我无法获取实时天气”。

有了 Function Calling，过程是：

  1. 应用告诉模型：”你有一个工具叫 get_weather，参数是城市名。”
  2. 模型判断需要查天气，输出：get_weather(city="广州")。
  3. 应用拿到这个请求，真正去调天气 API，得到”26℃、多云”。
  4. 应用把结果回填给模型。
  5. 模型基于结果回答：”广州今天多云，26 摄氏度。”

模型全程没有执行任何函数，它只做了两次决策：第一次决定”要调 get_weather”，第二次决定”拿到结果后怎么回答”。 这就是 Function Calling 的本质。

二、为什么需要它：模型的三道墙

大模型天生只会生成文本，面对真实任务时有三道墙：

  • 知识墙：训练数据有截止时间，不知道实时天气、最新订单状态。
  • 动作墙：不能发邮件、改数据库、调支付接口。
  • 私有数据墙：访问不到企业内部的文档和系统。

Function Calling 是翻过这三道墙的标准化方式：让模型表达“我需要外部能力”，由应用提供这些能力。它把”语言理解”和”系统执行”解耦，模型管理解与决策，应用管执行与安全。

三、机制：一次调用到底发生了什么

3.1 五个步骤

  1. 声明工具：应用把工具定义（名称、描述、参数 Schema）随请求一起传给模型。
  2. 模型决策：模型判断是否需要调用工具，若需要，输出结构化的调用请求。
  3. 应用执行：宿主程序解析请求，做权限校验、参数校验、超时重试，真正调用外部服务。
  4. 结果回填：把执行结果作为工具消息放回上下文。
  5. 模型继续生成：模型基于结果回答用户，或发起下一次调用。

这个循环可以重复多轮，直到模型不再发起调用。

3.2 谁生成调用请求？根据什么生成？

调用请求由模型本身逐 token 生成。它并不”查询”工具库，而是在生成时面对普通文本和”工具调用”特殊 token 做概率选择。

生成依据是应用每次请求中全量注入的工具定义 + 用户意图：

  • 工具名称：准确表达动作，如 query_order 而非 process。
  • 功能描述：影响意图匹配准确率最关键的部分。
  • 参数 Schema：类型、必填、枚举，决定模型能不能把参数填对。

另外，tool_choice 参数可以覆盖模型自主决策：auto 由模型判断，required 强制调用，none 禁止调用，也可指定具体工具。

3.3 一个容易被忽略的事实

每次请求，所有工具定义都会序列化为文本计入上下文 token。 工具越多，上下文开销越大，模型选择时的注意力也越容易被稀释。所以工程上常做动态工具注册：按角色或场景只暴露当前需要的工具子集，既控权限，也提准确率。

四、边界：它不是什么

清晰的定义也需要划清边界。

4.1 不是”模型自己执行函数”

模型输出的只是一段结构化数据。执行权、鉴权、幂等、副作用控制全在应用侧。不能把安全边界交给模型——它可能被提示注入诱导调用不该调的工具，也可能填错参数。

4.2 不是 RAG

  • RAG 是”注入知识”：把检索到的文档片段放进上下文。
  • Function Calling 是”触发查询或动作”：让模型主动调用外部工具。

两者常配合：RAG 管静态知识，Function Calling 管动态数据和操作。

4.3 不是 Agent 的全部

Agent = LLM + 工具 + 循环 + 规划/记忆。 Function Calling 是 Agent 使用工具的基础机制，但 Agent 还包含任务分解、多步规划、状态管理、失败恢复。Function Calling 是”手”，规划和记忆是”脑”。

4.4 不是”客户端自己决定调工具”

执行确实在客户端/应用侧，但**”调不调、调哪个、传什么参数”由模型生成**。没有模型这一步决策，应用直接调 API，那只是普通程序调用，不叫 Function Calling。

五、工程落地：关键不在”能调”，而在”调得对、调得稳”

5.1 工具描述质量

名称和 description 决定模型选不选得对，参数 Schema 决定填得对不对。实践中：用动词开头的清晰名称；描述里写明适用和不适用场景；参数尽量用枚举、必填标记和格式约束。

5.2 错误处理

工具失败要返回结构化错误，让模型能重试、换工具或向用户解释。不要把原始异常堆栈直接塞回上下文。

5.3 结果裁剪

工具返回太长会挤爆窗口。需要摘要、字段裁剪、分页，只保留模型决策所需的关键信息。这是 Context Engineering 的典型战场。

5.4 安全

权限最小化、参数二次校验、防提示注入、敏感操作人工确认、幂等和审计。模型输出不可信，应用侧必须兜底。

5.5 可观测性

记录每轮调用了什么、参数是什么、耗时多少、结果如何、失败原因是什么，形成可迭代的闭环。

六、与 MCP 的关系：一个管”怎么接”，一个管”怎么说”

常见误解是”Function Calling 的上游是 MCP 输出的数据”。准确关系是：

  • Function Calling 是模型侧的决策机制：决定”要不要调、调哪个、传什么参数”。
  • MCP 是应用侧的连接协议：规范”工具怎么被发现、怎么被调用”。

链路是：MCP Server 暴露工具 → 客户端发现并转换成模型能识别的格式 → 模型生成调用请求 → 应用执行（可能经 MCP Client 转发）→ 结果回填模型。

所以 MCP 提供的是工具来源，不是直接喂给 Function Calling 的上游数据。一句话：MCP 管”工具从哪来、怎么接”，Function Calling 管”模型怎么表达要调它”。

七、角色分层：Agent、客户端、MCP Client 别混

  • Agent（决策层）：LLM 驱动，负责理解任务、规划、决定调哪个工具、根据结果继续推理。关心”做什么、为什么做”。
  • 客户端/应用（宿主层）：承载 Agent，组装上下文、传工具 Schema、解析 tool_calls、执行或转发、回填结果、做权限审计。关心”怎么安全可靠地接进来并执行”。
  • MCP Client（协议层）：宿主里的组件，负责连 MCP Server、发现工具、发起 tools/call、收结果。不决定”该不该调”，只负责”按协议送达”。

关系：Agent 跑在客户端/宿主里；宿主里包含 MCP Client；MCP Client 连 MCP Server。

八、结语

Function Calling 的价值不在于”让模型能调函数”，而在于建立了一套清晰的责任边界：模型负责语言理解和调用意图生成，应用负责执行、安全和治理。

理解这一点，才能避免两个误区：既不要把 Function Calling 神化为”模型自己会执行”，也不要把工具接入的所有问题都归咎于模型”不够聪明”。模型决定”调不调、调哪个”；应用决定”接得稳不稳、执行得对不对”。 两者配合，才让大模型从”会说”真正走向”会做”。

本版相对上一版的核心改动：开篇用三句话定义 + 一个贯穿场景先回答”是什么”；新增”为什么需要它”和”它不是什么”两节划清边界；把”客户端自己决定调工具”这个常见误解显式写进边界；全文围绕”模型说、应用做、结果回填”这一主线组织，避免读者读完仍停留在流程细节里。
