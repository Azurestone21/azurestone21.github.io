Context Engineering 上下文工程

Context Engineering 上下文工程

一、定义

Context Engineering 是设计并管理模型推理时整个信息环境的工程学科：决定模型看到什么、记住什么、忽略什么，让关键信息在决策那一刻恰好出现。

它不是 Prompt Engineering 的替代，而是它的上位概念。Prompt 管“怎么说”，Context 管“让模型在什么信息环境里做决策”。

二、由来与推动者

2025 年中，Shopify CEO Tobi Lütke 在 X 上提出“Context Engineering 比 Prompt Engineering 更贴切”。Andrej Karpathy 转发认同，并给出关键判断：工业级 LLM 应用中，上下文工程才是核心——要把上下文窗口精确填入下一步所需的信息。

Gartner 随后将其定义为：设计并结构化相关数据、工作流和环境，使 AI 系统无需依赖手动提示即可理解意图并做出企业对齐的决策。

三、上下文包含什么（六类来源）

一个生产级 AI 系统的上下文窗口通常由以下成分构成：

成分 说明 工程关注点
系统指令 角色、约束、输出格式 稳定放前缀，走缓存
用户输入 当前任务 不可避免，需解析
对话历史 本轮交互记录 需裁剪、摘要
长期记忆 跨会话偏好、决策 按需注入，控制体积
外部检索 RAG 片段、文档 相关性优先，防噪声
工具定义与输出 Function Calling Schema、返回结果 裁剪、落盘、留指针

上下文不是“越多越好”：Chroma 等研究及 2026 年多篇论文确认，输入上下文增长时模型输出质量会下降，即使远未达到窗口上限——这被称为“context rot”（上下文腐烂）。Anthropic 的实验数据显示：上下文 8K 以下时关键信息召回率 95%+，32K 时降到 78%，100K 时“视而不见”的概率升至 30%。

四、与 Prompt Engineering 的本质区别

维度 Prompt Engineering Context Engineering
优化对象 单次指令的措辞 整个信息环境与系统架构
时间尺度 静态、一次性 动态、每步持续策展
问题边界 指令是否清晰 该进窗口的信息是否进来、噪声是否挤占
适用场景 单轮、无状态任务 Agent、长任务、RAG 系统

Prompt 是 Context 的一个子集。单轮格式转换、文案起草，Prompt Engineering 仍然高效；但做 Agent、长任务、多工具编排时，只优化 Prompt 会碰到天花板，因为模型访问不到信息、窗口被噪声占满、跨轮记忆丢失——这些不是措辞能解决的。

五、核心工程实践

5.1 围绕 KV-Cache 设计（Manus 的第一原则）

Manus 团队指出：KV-cache 命中率是生产 Agent 最重要的单一指标。Claude Sonnet 缓存输入 $0.30/百万 token，未缓存 $3/百万——差 10 倍。

三条规则：

  • 保持提示前缀稳定：不要在系统提示开头放时间戳（尤其精确到秒），否则每轮缓存全失效。
  • 上下文只追加，不修改：避免回头改之前的内容，确保序列化确定性（JSON 键顺序稳定）。
  • 需要时显式标记缓存断点：部分框架不支持自动增量缓存，需手动插入。

5.2 工具管理：遮蔽，而非移除

工具数量爆炸时，Manus 的教训是：不要在中途动态增删工具定义。因为工具定义通常位于上下文前部，改动会摧毁后续所有 KV-cache；且旧调用记录引用已不存在的工具时，模型会困惑。

替代方案：用状态机 + logit 遮蔽限制当前可选的工具子集，而不修改上下文中的工具定义。行动名称用统一前缀（如 browser_*、shell_*）帮助模型在子集内选择。

5.3 历史剪裁的分级策略

按成本从低到高触发：

第一层：裁工具输出（零成本）。旧 tool result 只保留头尾，中间用占位符，但必须留下“完整内容在哪、怎么取”的指引，否则模型不知道信息缺失。

第二层：滑动窗口丢弃旧轮次（零成本）。按完整交互轮次切割，保护工具调用与结果的配对关系。

第三层：LLM 摘要（有成本）。把旧消息压缩为一条交接摘要，保留目标、约束、关键决策、未解决问题。Manus 的输入输出比约 100:1，不做压缩成本会失控。

5.4 长任务的“三把刀”（Anthropic 总结）

  • Compaction（压缩）：接近窗口上限时，让模型总结历史，丢弃冗余工具输出，保留架构决策和未解决问题，用摘要开新窗口继续。
  • 结构化笔记：窗口外维护持久记忆文件，Agent 按需读写，实现跨会话连续性。
  • 子 Agent 架构：把探索性搜索交给子 Agent，它返回 1000-2000 token 的摘要给主 Agent，保护主 Agent 的上下文预算。

六、与 Function Calling / MCP 的关系

Function Calling 是 Context Engineering 的重要输入源，也是消耗窗口的大户。

每次工具调用都向上下文追加：工具定义（常驻）、调用参数、返回结果、错误信息。一个 Agent 运行几十轮后，工具日志可能占据窗口的大部分。因此 Context Engineering 必须管理工具上下文的生命周期：哪些工具定义常驻、返回结果如何裁剪、调用历史保留多久、错误信息如何压缩。

MCP 管“工具从哪来、怎么接”，Function Calling 管“模型怎么表达要调它”，Context Engineering 管“这些工具信息怎么在窗口里被策展和治理”。 三者层次不同，但协同工作。

七、总结

问题 答案
Context Engineering 是什么？ 设计模型推理时整个信息环境，决定看到什么、记住什么、忽略什么
和 Prompt 什么关系？ Prompt 是子集，Context 是上位；Prompt 管“说”，Context 管“看什么”
为什么重要？ 上下文增长会导致质量下降（context rot），必须策展而非堆砌
最核心的工程指标？ KV-cache 命中率（Manus 观点）
工具太多怎么办？ 遮蔽 logit，不要动态增删工具定义
历史太长怎么办？ 先裁工具输出，再丢旧轮次，最后摘要兜底
和 Prompt 什么区别？ Prompt 让模型听懂这次任务，Context 让模型在正确信息环境中持续做对决策

Context Engineering 不是“写更好的提示词”，而是“为模型的每一次决策搭建恰好够用的信息舞台”。 它把上下文窗口当作有限资源来治理，用缓存、裁剪、摘要、外置记忆和工具策展，让模型在长任务中不迷失、不腐烂、不爆窗。
