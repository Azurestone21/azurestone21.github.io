Git 面试重点

Git 面试重点

一、基础概念

1. Git 是什么？和 SVN 有什么区别？

Git 是分布式版本控制系统，每个开发者本地都有完整仓库和历史。SVN 是集中式，依赖中央服务器。
Git 分支轻量、离线可提交、合并强；SVN 分支重、依赖网络。

2. 工作区、暂存区、版本库、远程仓库分别是什么？

  • 工作区：本地可见文件目录。
  • 暂存区 / index：git add 后进入的区域。
  • 版本库：.git 目录，保存提交历史。
  • 远程仓库：GitHub / GitLab 等。
    流程：工作区 → git add → 暂存区 → git commit → 版本库 → git push → 远程仓库。

3. HEAD 是什么？

HEAD 是指向当前分支最新提交的指针。通常指向分支，也可以直接指向某个提交，即 detached HEAD。

4. git fetch 和 git pull 的区别？

  • git fetch：只拉取远程更新，不合并。
  • git pull：fetch + merge 或 fetch + rebase。
    推荐先 fetch，再决定 merge 或 rebase。

6. git clone 和 git init 的区别？

  • git init：初始化本地空仓库。
  • git clone：从远程复制完整仓库，包括历史和远程配置。

7. git add 和 git commit 到底做了什么？

  • git add：把文件快照放入暂存区。
  • git commit：把暂存区快照生成一次提交。

二、分支与合并

1. Git 分支的本质是什么？为什么快？

分支本质是一个指向提交的可变指针。创建分支只是新建一个指针，几乎不复制文件，所以非常快。

2. merge 和 rebase 的区别？

  • merge：保留分支历史，产生合并提交。
  • rebase：把提交重放到新基点，历史线性，但会重写 commit hash。
    公共分支慎用 rebase，个人分支适合 rebase 整理历史。

3. 什么是 fast-forward merge？

当目标分支没有新提交时，Git 直接把分支指针向前移动，不产生合并提交。

4. 如何解决冲突？

见后文”冲突专题”。基本流程：手动编辑冲突文件 → git add → 根据操作执行 git merge --continue 或 git rebase --continue。

三、撤销与回退

1. git reset 三种模式的区别？

  • --soft：只移动 HEAD，暂存区和工作区不变。
  • --mixed（默认）：移动 HEAD，重置暂存区，工作区不变。
  • --hard：移动 HEAD，重置暂存区和工作区，危险，会丢修改。

2. reset 和 revert 的区别？

  • reset：回退历史，重写提交，适合本地未推送。
  • revert：创建一个新提交来抵消旧提交，适合公共分支。

六、Git 内部原理：Git 是如何管理代码的？

1. Git 管理代码的核心模型是什么？

一句话：Git 用”内容寻址的不可变对象数据库”保存代码快照，用”可变引用”指向提交历史，用”暂存区”连接工作区和版本库。

它不是简单保存文件差异，而是把每次提交都当作一次完整快照来管理，只是通过共享未变化的对象和打包压缩来节省空间。

2. 什么是内容寻址和 Merkle DAG？

Git 把代码、目录、提交都变成对象，每个对象用内容的 SHA-1 哈希命名。

4. 引用、分支、HEAD 的本质是什么？

对象不可变，但引用可变。

  • 分支：指向某个 commit 的指针。
  • 标签：指向某个 commit 的固定引用。
  • HEAD：指向当前分支，通常内容是 ref: refs/heads/main。
  • 远程跟踪分支：如 refs/remotes/origin/main。
    创建分支只是新建一个指针文件，所以非常快。

5. 三个区域与提交流程是什么？

  1. 工作区：看到的文件。
  2. 暂存区 / 索引：git add 后进入的区域。
  3. 版本库：.git 目录，保存所有对象和引用。

6. 分支、合并、rebase 的本质是什么？

因为分支只是指针，所以：

  • 切换分支：更新 HEAD，检出对应 tree 内容。
  • 快进合并：直接移动分支指针。
  • 普通合并：找共同祖先，三方合并，生成新 tree 和 merge commit。
  • rebase：把提交依次重放到新基点，生成新 commit，哈希改变。

7. Git 如何保证完整性和节省空间？

  • 每个对象都有哈希。
  • tree 哈希由子对象哈希决定。
  • commit 哈希由 tree、parent、作者、提交信息等决定。
  • 改动任何内容都会导致哈希变化。
  • 物理上，松散对象会打包成 packfile，可能使用 delta 压缩，但逻辑模型仍是快照。
  • 默认 SHA-1，现在也支持 SHA-256。

8. 总结：Git 管理代码的方式

  • 代码内容存成 blob。
  • 目录结构存成 tree。
  • 提交历史存成 commit。
  • 分支和 HEAD 只是指向 commit 的可变引用。
  • 每次提交是完整快照，但通过哈希去重和 packfile 压缩节省空间。
  • 合并、rebase、reset、cherry-pick 本质上都是在操作这些对象和引用。

七、冲突专题：Git 冲突是什么时候发生的？正确处理流程？

1. Git 冲突是什么时候发生的？

一句话：当 Git 无法自动合并两边的修改时，就会发生冲突。

底层看，Git 合并时通常做”三方合并”：

  • base：共同祖先
  • ours：当前分支
  • theirs：要合并进来的分支

如果同一个文件的同一区域，在两边都有不同修改，Git 无法判断该保留谁，就会冲突。

常见触发场景：

  1. git merge feature
  2. git rebase main
  3. git cherry-pick <commit>
  4. git pull 或 git pull --rebase
  5. git stash pop / apply
  6. 文件删除、重命名、修改冲突：一边修改，另一边删除；或重命名后另一边又修改。

不是所有同时修改都会冲突。改不同文件，或同一文件不同区域，Git 通常能自动合并。

2. 冲突文件长什么样？

含义：

  • <<<<<<< HEAD 到 =======：当前分支 / 当前基点内容。
  • ======= 到 >>>>>>>：传入分支 / 被重放提交内容。

注意：rebase 中 ours 和 theirs 含义会反转。

  • merge 时：ours = 当前分支，theirs = 被合并分支。
  • rebase 时：ours = 正在变基到的目标分支，theirs = 你正在重放的提交。
    不要死记 ours/theirs，要看 git status 和提交来源。

5. 面试口述模板

Git 冲突发生在 merge、rebase、cherry-pick、pull、stash pop 等操作中，当同一文件同一区域两边都有不同修改，Git 无法自动合并时就会冲突。
正确处理流程是：先用 git status 确认操作类型和冲突文件，然后打开文件解决 <<<<<<<、=======、>>>>>>> 标记，保留正确内容，git add 标记已解决，再根据操作执行 git merge --continue、git rebase --continue 或 git cherry-pick --continue，最后跑测试再提交或推送。
如果不想继续，可以用对应的 --abort 放弃。rebase 中要注意 ours/theirs 含义反转，公共分支不要随便强推。

6. 预防冲突

  • 小步提交
  • 频繁同步主分支
  • 统一代码格式化
  • 避免多人长期改同一区域

八、面试加分总结

  • 能说清 工作区、暂存区、版本库 的数据流。
  • 能区分 merge / rebase / cherry-pick / revert / reset。
  • 知道 rebase 黄金法则：不要 rebase 已共享的公共分支。
  • 会用 reflog 救火。
  • 能结合团队工作流讲：PR、Code Review、CI、分支策略。
  • 强推优先用 --force-with-lease，不用 --force。
  • 理解 Git 内部是 内容寻址的对象数据库 + 引用 + 快照。
  • 冲突处理要按 确认状态 → 解决 → add → continue → 测试 的流程走。
