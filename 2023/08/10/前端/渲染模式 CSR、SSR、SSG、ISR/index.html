渲染模式 CSR、SSR、SSG、ISR

渲染模式 CSR、SSR、SSG、ISR

区分这四种模式，只需要问两个问题：

  1. HTML 在哪里生成？ 服务器 / 浏览器 / 构建时
  2. 什么时候生成？ 每次请求时 / 构建时 / 后台定时或按需
模式 生成地点 生成时机
CSR 浏览器 运行时（用户访问后）
SSR 服务器 每次请求时
SSG 服务器/构建机 构建时（一次）
ISR 服务器 构建时 + 后台按需/定时再生

一、CSR（Client-Side Rendering，客户端渲染）

工作流程

  1. 浏览器请求页面
  2. 服务器返回一个几乎空的 HTML（通常只有一个 <div id="root">）和 JS bundle
  3. 浏览器下载、解析、执行 JS
  4. JS 请求数据（API）
  5. JS 把内容渲染进 DOM，用户才看到页面

特点

  • 首屏白屏时间长：要等 JS 下载 + 执行 + 数据请求完成
  • SEO 弱：早期爬虫拿到的 HTML 是空的（现代 Google 能执行 JS，但不稳定）
  • 服务器压力小：只发静态文件，容易 CDN 加速
  • 首屏之后体验流畅：路由切换不刷新页面，像原生 App

典型场景

  • 后台管理系统（Admin Dashboard）
  • 登录后的 SaaS 应用
  • 交互极重、SEO 不重要的页面

代表技术

React（纯 CRA/Vite）、Vue（纯 Vite）、Angular

二、SSR（Server-Side Rendering，服务端渲染）

工作流程

  1. 浏览器请求页面
  2. 服务器执行前端组件代码，同时取数据
  3. 服务器把组件渲染成完整 HTML 返回
  4. 浏览器立即显示内容（首屏快）
  5. JS 加载后执行 hydration（注水），页面变为可交互

特点

  • 首屏快：HTML 直达，用户马上看到内容
  • SEO 好：HTML 里有完整内容
  • 服务器压力大：每次请求都要渲染 + 取数据
  • TTFB 可能变高：服务器要先干活才能响应
  • 注水前不可交互：能看到但不能点，注水完成后才正常
  • 开发复杂：要处理服务端/客户端环境差异（如 window、document 不存在）

典型场景

  • 电商商品页（SEO + 首屏速度都重要）
  • 新闻/内容网站
  • 需要个性化 + SEO 的页面

代表技术

Next.js（getServerSideProps / Server Components）、Nuxt（ssr: true）、Remix、SvelteKit

三、SSG（Static Site Generation，静态站点生成）

工作流程

  1. 构建时（npm run build），框架把所有页面预渲染成 HTML 文件
  2. 部署时把这些 HTML 放到 CDN/静态服务器
  3. 用户请求时，直接返回对应的静态 HTML
  4. 浏览器加载 JS 后注水，变为可交互

特点

  • 最快：纯静态文件，CDN 边缘直接返回，TTFB 极低
  • SEO 最好：HTML 完整
  • 服务器成本最低：几乎不需要运行时服务器
  • 数据是构建时的快照：内容更新必须重新构建 + 部署
  • 不适合频繁变动的数据：比如实时价格、个性化内容

典型场景

  • 博客、文档站
  • 营销落地页
  • 企业官网
  • 内容更新不频繁的电商分类页

代表技术

Next.js（getStaticProps）、Nuxt（ssr: false + generate）、Astro、Gatsby、Hugo、Eleventy

四、ISR（Incremental Static Regeneration，增量静态再生）

ISR 是 SSG 的进化版，解决“静态页面数据会过期”的问题。它是 Next.js 提出的概念。

工作流程（以 Next.js 为例）

  1. 构建时预渲染页面（和 SSG 一样）
  2. 部署到服务器/CDN
  3. 用户请求页面 → 先返回当前缓存的静态 HTML（快）
  4. 同时后台判断是否超过设定的 revalidate 时间
  5. 如果过期，后台异步重新生成该页面
  6. 下一个用户请求就能拿到新版本

两种触发方式

  • 时间驱动（revalidate）：如 revalidate: 60，表示 60 秒后下次请求触发再生
  • 按需驱动（on-demand）：通过 API 手动触发某个页面再生，适合内容发布后立即更新

特点

  • 兼具 SSG 的速度和 SSR 的数据新鲜度
  • 用户永远拿到静态 HTML，不会被阻塞
  • 数据有一定延迟：不是实时的，是“最终一致”
  • 需要支持 ISR 的托管平台（如 Vercel、Netlify，或自建配合缓存）

典型场景

  • 电商商品列表/详情（价格、库存可容忍几分钟延迟）
  • 新闻站点（新文章发布后按需再生）
  • 大型内容站（页面多，不可能全部重新构建）

代表技术

Next.js（revalidate）、Nuxt（配合混合渲染）、Astro（配合 SSR 适配器）

五、四者横向对比

维度 CSR SSR SSG ISR
HTML 生成时机 运行时（浏览器） 每次请求 构建时 构建时 + 后台再生
首屏速度 慢 快 最快 最快
SEO 差 好 好 好
数据新鲜度 实时 实时 构建时快照 准实时（有延迟）
服务器压力 低 高 极低 低
可扩展性 高 中 极高 高
适用内容 重交互 动态 + SEO 静态内容 大量动态内容

六、实际项目往往是混合的

现代框架（Next.js App Router、Nuxt 3、SvelteKit）允许同一项目里不同路由用不同策略：

  • 首页/营销页 → SSG
  • 商品详情页 → ISR
  • 用户订单页 → SSR（需要登录态）
  • 后台管理 → CSR

这就是所谓的 混合渲染（Hybrid Rendering），也是现在主流的做法。

七、怎么选：一个简单决策树

  1. 页面需要 SEO 吗？
    • 不需要 → CSR
    • 需要 → 继续
  2. 内容对每个用户不同，或需要实时数据吗？
    • 是 → SSR
    • 否 → 继续
  3. 内容更新频繁吗？
    • 不频繁 → SSG
    • 频繁但可容忍延迟 → ISR
