MobX 核心：计算值（Computed）

MobX 核心：计算值（Computed）

1. 核心定义

computed 是基于现有可观察状态（Observable）派生出的新值。它就像一个电子表格的公式，依赖变化时自动更新。

  • 本质：派生状态（Derived State），由其他状态计算而来。
  • 原则：
    • 纯净：无副作用，不修改任何外部状态。
    • 同步：计算过程必须是同步的，不能包含异步操作。
    • 确定性：相同输入永远得到相同输出。

2. 核心工作机制（高性能关键）

  • 懒执行（Lazy Evaluation）：只有被外部读取时才会计算。没人读，它就不干活。
  • 智能缓存（Smart Caching）：依赖不变，多次读取直接返回缓存值，绝不重复计算。
  • 自动挂起（Suspension）：当没有任何观察者（如 UI 组件）依赖它时，自动取消对上游依赖的监听，释放内存。

3. 基本用法（Class 组件）

4. 计算值的 Setter（逆向修改）

computed 的 setter 不是用来直接修改缓存结果的，而是用来逆向推导并修改原始依赖数据。

规则提醒：

  • ❌ 禁止在 setter 中产生副作用（异步请求、操作 DOM）。
  • ❌ 禁止在 setter 中给自身赋值（this.fullName = xx），会死循环。
  • ✅ 如果逆向逻辑复杂（含校验），推荐改用普通的 Action 函数代替。

5. 底层感知机制（怎么知道被读取了？）

computed 通过维护一个 observers（观察者列表） 来判断：

  1. 有观察者：说明被读取中，保持激活，监听上游变化。
  2. 无观察者：说明未被读取，进入挂起，立即释放资源。
  3. 检查方式：依赖全局指针 globalState.trackingDerivation。
    1. 当响应式上下文（如 autorun）读取它时，computed 的 getter 被触发，将上下文加入自己的 observers 列表。
    2. 这个过程是按需触发，O(1) 复杂度，无全局扫描。

6. 响应失灵：常见场景与排查

6.1 依赖了非可观察对象（Non-Observable）

现象：computed 依赖的变量发生变化，但计算值纹丝不动。

原因：MobX 的响应式系统只能追踪可观察对象（Observable） 的变化。如果 computed 内部读取的是普通变量、localStorage、sessionStorage 等，MobX 无法感知其变化，自然不会触发重新计算。

6.2 没有被任何 Reaction 使用（无观察者）

现象：在 autorun 或 observer 组件之外读取 computed，发现每次读取都会重新计算，缓存似乎失效了。

原因：computed 采用懒执行 + 自动挂起策略。如果没有任何 Reaction（如 autorun、observer 组件）在使用它，MobX 认为它“不活跃”，不会缓存结果。每次读取都会重新计算，就像普通函数一样。

解决方案：

方案 说明
keepAlive: true 强制保持活跃，即使无观察者也缓存结果
computedRequiresReaction: true 开发模式下，在非响应式上下文中访问时抛出错误，帮助提前发现问题

6.3 在 Action 内部多次读取，拿到旧值（Atom 相关）

现象：在同一个 action 中，修改了依赖数据后再次读取 computed，返回的却是旧值。

原因：当 computed 背后使用的是自定义 Atom 时，在 action 内部，数据变化后 computed 的缓存没有立即失效，导致第二次读取时仍返回旧值。而普通的 observable.box 不会有此问题。

解决方案：这是一个已知的边缘情况。建议：

  • 尽量使用 MobX 内置的 observable 类型，而非手动创建 Atom。
  • 若必须使用 Atom，在 action 中读取 computed 后，可通过 runInAction 或 transaction 来规避。

6.4 computed 返回新对象/新引用

现象：computed 每次返回一个内容相同但引用不同的新对象，导致依赖它的 observer 组件无限重渲染。

原因：MobX 的 computed 默认通过浅比较来判断结果是否变化。如果返回的是对象、数组等引用类型，即使内容相同，每次计算都会产生新引用，MobX 会认为值发生了变化，从而触发所有下游观察者。

6.5 异步函数中的依赖追踪中断

现象：在 computed 的 getter 中使用了 async/await，发现 await 之后的代码不再追踪依赖。

原因：MobX 的依赖追踪是同步的。当函数执行到第一个 await 时，执行上下文被挂起，后续代码在微任务中恢复执行，此时 MobX 的全局追踪上下文已丢失，无法追踪 await 之后的依赖。

解决方案：

  • computed 应该是同步纯函数，不应包含异步逻辑。
  • 异步逻辑应放在 flow 或 action 中，将结果写入 observable，再由 computed 读取。

6.6 在 computed 内部修改可观察对象（副作用）

现象：computed 的行为变得不可预测，有时更新有时不更新。

原因：computed 应该是无副作用的纯函数，不应该修改任何可观察对象。在 computed 内部修改状态会破坏 MobX 的响应式推断，导致难以调试的问题。

6.7 带参数的计算值（computed 无法接受参数）

现象：需要根据参数计算派生值，但 computed 的 getter 不支持参数。

原因：computed 注解只能用于无参数的 getter。

解决方案：

方案 适用场景
直接用普通函数 最简方案，MobX 依然能追踪其内部依赖
在组件内创建临时 computed 需要缓存特定参数的计算结果时
调整状态设计 将计算结果（如 isSelected）直接作为状态存储
computedFn（mobx-utils） 带参数的记忆化计算，适合复杂场景

6.8 子类继承时未使用 override 注解

现象：子类重写了父类的 computed 属性，但子类的计算值不生效。

原因：在子类中重写父类的 computed 时，需要使用 override 注解，否则 MobX 无法正确处理继承链中的计算值。

快速排查清单

问题现象 可能原因 解决方案
