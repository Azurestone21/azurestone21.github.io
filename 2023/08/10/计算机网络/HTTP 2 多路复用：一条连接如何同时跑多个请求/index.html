HTTP 2 多路复用：一条连接如何同时跑多个请求

HTTP 多路复用：一条连接如何同时跑多个请求

如果你经历过 HTTP/1.1 时代的前端优化，一定对”域名分片””雪碧图””合并 JS/CSS”这些手段不陌生。它们有一个共同的敌人：队头阻塞。而它们的共同解药，就是 HTTP/2 带来的多路复用。

这篇文章想讲清楚一件事：多路复用到底是怎么实现的，为什么它能做到”一条连接上同时交错传输多个请求和响应”。

一、先看问题：HTTP/1.1 为什么只能串行

HTTP/1.1 引入了 keep-alive，一条 TCP 连接可以承载多个请求，听起来不错。但实际行为是这样的：

问题出在 HTTP 报文的文本格式上。HTTP/1.1 的报文是一段连续文本，接收方靠 Content-Length 或 chunked 编码来判断”这条报文到哪结束”。一旦开始读一条报文，就必须读完才能开始下一条——字节流里没有机制区分”这个字节属于请求 A 还是请求 B”。

结果是：一条连接同一时刻只有一个请求在”飞”。A 如果是个大文件，B 就得干等。这就是 HTTP 层的队头阻塞。

浏览器的应对办法是”多开几条连接”——每个域名开 6 条左右，用不同车道绕开阻塞。但连接本身有成本（三次握手、TLS 握手、慢启动），开到 6 条已是极限，再想并行就只能靠域名分片这种”骗浏览器”的手段。

根本矛盾是：一条连接无法在字节流层面区分多个请求。 多路复用要解决的，就是这个。

二、多路复用的核心：把报文拆成带标签的帧

HTTP/2 的答案很直接：不再传文本报文，改传二进制帧。

一条 HTTP 请求或响应被拆成更小的帧（Frame），每个帧头部带一个关键字段：

字段 作用
Length 帧载荷长度，用于在字节流中切出帧边界
Type 帧类型（HEADERS、DATA、SETTINGS、RST_STREAM 等）
Flags 标志位（如 END_HEADERS、END_STREAM）
Stream Identifier 流 ID——这个帧属于哪个请求/响应

Stream Identifier 就是那个”标签”。 有了它，接收方就能从混在一起的字节流里，把属于不同请求的帧重新归组。

一条请求的报文被拆成：

  • HEADERS 帧：承载请求/响应头（经 HPACK 压缩）
  • DATA 帧：承载正文，可能拆成多块

于是，原本”一条报文一段连续文本”的结构，变成了”若干带流 ID 的帧”。

三、流：逻辑上的独立通道

流（Stream） 是 HTTP/2 的逻辑概念，代表一次完整的请求-响应交换，每个流有唯一整数 ID。

  • 客户端发起的流用奇数 ID（1、3、5…）
  • 服务端发起的流用偶数 ID（2、4、6…）
  • 流 ID 单调递增，不复用

流是独立的：流 1 的帧和流 3 的帧可以在连接上任意交错，接收方各归各的流处理。流在逻辑上隔离，帧在物理上交错——这就是多路复用能成立的结构基础。

四、交错发送：多路复用的实际形态

假设客户端要请求 /a.html（流 1，响应很大）和 /b.css（流 3，响应很小）。一条连接上的字节流可能是：

b.css 的响应完全插在 a.html 的响应中间传输。客户端按流 ID 重组：

  • 流 1 → HEADERS + DATA + DATA = 完整 a.html 响应
  • 流 3 → HEADERS + DATA = 完整 b.css 响应

这里有两个容易误解的点：

① 交错是双向的。 不只是服务端返回响应时交错，客户端发请求时也可以交错——[HEADERS 流1] 后不必等响应，可以直接发 [HEADERS 流3]。请求方向和响应方向是两条独立字节流，各自交错，靠流 ID 配对。

② 协议不规定跨流帧的顺序。 [HEADERS 流1] 后直接跟 [DATA 流1] 完全合法。上面例子”HEADERS 集中在前”只是实现中常见的调度结果（头小且生成快，正文大需调度），不是协议要求。

五、为什么不会乱：三重保障

1. 帧边界靠 Length 字段。 TCP 是字节流没有消息边界，HTTP/2 靠帧头的 Length 在字节流中切出一个个帧。TCP 保证字节有序，所以帧本身不会乱序。

2. 归组靠流 ID。 帧到达后按 Stream Identifier 放进对应流的缓冲区，跨流交错、流内有序。

3. 流级流量控制。 HTTP/2 有连接级和流级两套流量控制（WINDOW_UPDATE 帧）。每条流独立控速，慢流不会耗尽整条连接的缓冲，也不会挤占其他流的带宽——这保证交错是公平的，而不是快流饿死慢流。

此外还有流优先级（依赖树 + 权重）供调度器参考，让关键资源优先发送，但优先级只是建议，不强制。

六、多路复用的收益

对比项 HTTP/1.1 串行 HTTP/2 多路复用
请求发起 必须等前一个响应完成 可立即并发发起
慢请求影响 阻塞后续所有请求 只影响自己的流
连接数 每域名 6~8 条绕开阻塞 一条足够
头部开销 每条请求重复完整头部 HPACK 压缩 + 头部表复用

核心收益是消除了 HTTP 层的队头阻塞，同时把连接数从”多条”降到”一条”，省去大量握手和慢启动开销。

七、局限：TCP 层队头阻塞还在

这是多路复用最容易被忽略的坑。HTTP/2 只解决了 HTTP 层的队头阻塞，没有解决 TCP 层的。

TCP 保证字节流严格有序。假设连接上交错着流 1 和流 3 的帧，某个承载流 1 数据的 TCP 包丢了：

TCP 必须按序交付，包 4、5 即使到了也要等包 3 重传成功才能交给应用层。整条连接上所有流一起被阻塞，直到丢包恢复。

所以多路复用有个隐含前提：网络不能丢包。一旦丢包，复用优势会被 TCP 的按序交付抵消。这正是 HTTP/3 改用 QUIC 的根本动机——QUIC 在 UDP 上实现流级的可靠有序传输，丢包只影响所属流，不波及其他流。HTTP/3 才真正同时消除了 HTTP 层和传输层的队头阻塞。

八、回到那个问题：多路复用是什么

多路复用不是”多个请求共用一条 TCP 连接”那么简单。 HTTP/1.1 的 keep-alive 也共用连接，但它是串行复用，同一时刻只有一个请求在飞，照样队头阻塞。

多路复用的本质是：通过二进制分帧 + 流 ID，让多个请求/响应在同一条连接上同时、交错地传输，彼此不阻塞。 共用连接是载体，帧级交错才是灵魂。

它的技术要件可以概括为四件事：

  1. 帧化——把报文拆成带流 ID 的小帧，让字节流可区分
  2. 流——每个请求-响应是独立逻辑通道
  3. 流级流量控制——慢流不拖累快流
  4. （可选）优先级——调度器决定先发谁

理解了这四点，也就理解了 HTTP/2 相对 HTTP/1.1 的核心跃迁，以及它为什么还需要 HTTP/3 来补上传输层那最后一块短板。
