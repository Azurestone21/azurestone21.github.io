二、读懂分析报告

2.1 三个核心体积指标

指标 含义 优化参考价值
Stat size 源码在磁盘上的原始大小（含注释、未使用代码） ⭐ 较低，仅用于对比 Tree Shaking 效果
Parsed size Webpack 打包后的实际代码体积（未压缩） ⭐⭐⭐ 最重要，直接决定主包大小
Gzipped size Gzip 压缩后的传输体积 ⭐⭐ 影响用户加载速度，约等于 Parsed 的 20%~30%

优化原则：以 Parsed size 为优化目标，用 Gzipped size 衡量加载性能改善。

2.2 检查重复打包

  1. 勾选分析器左侧的 “Show content of concatenated modules”（可展开模块内部结构）。
  2. 在 “Search modules” 中输入库名（如 lodash）。
  3. 查看该库是否出现在多个 chunk 中——若是，则存在重复打包。

原理：Webpack 默认开启作用域提升（Module Concatenation），将多个小模块合并到同一闭包中。开启该选项后，分析器会按比例估算每个子模块的体积（数值不精确，但相对大小足以指导优化）。

4.1 common.js 体积构成分析

分析报告显示 common.js 包含大量 src/shared 下的模块：

  • UI 组件（Skeleton、AiUpdateDialog、QuickContact 等）
  • Canvas 绘图工具（canvasShareBg.ts、canvasGreetingPoster.ts）
  • API 服务（card.ts、privateChat.ts、enterpriseCard.ts）
  • 自定义 Hooks（useCardDetail、useExchange 等）
  • 工具函数（storage.ts、eventBus.ts）

4.2 优化策略：按分包归属迁移

模块 使用场景 迁移目标
canvasShareBg.ts / canvasGreetingPoster.ts 生成分享/祝福海报 src/pages/packageCard/utils/canvas/
AiUpdateDialog AI 更新弹窗 src/pages/packageCard/components/
privateChat.ts API 仅用于私聊分包 src/pages/packageUser/services/
enterpriseCard.ts API 仅用于企业名片分包 src/pages/packageEnterprise/services/

核心原则：

  • 只被主包页面引用的模块 → 保留在 src/shared
  • 只被分包页面引用的模块 → 迁移到对应分包目录
  • 被多个分包共享、但不被主包引用的模块 → 移至 src/pages/packageCommon/

六、总结

核心方法论

  1. 用数据驱动优化：通过 webpack-bundle-analyzer 定位体积大头，而非盲目优化。
  2. 优先用自动优化：Taro 的 optimizeMainPackage 能低成本解决大部分分包依赖问题。
  3. 按需引入是关键：检查大型库是否全量引入，使用 babel-plugin-import 或 babel-plugin-lodash 等工具自动化处理。
  4. 合理划分代码归属：将只服务于分包的模块移出主包 shared 目录，避免污染主包 common.js。
  5. 阈值是最后手段：在无法继续优化的刚性依赖上，适度调高 Webpack 阈值以消除无效警告。

后续建议

  • 定期（如每季度）重新生成分析报告，防止体积回弹。
  • 新增依赖时，先检查其体积（可使用 npm info <pkg> --json 查看）。
  • 考虑使用 dayjs 替代 moment、使用 lodash-es 配合 Tree Shaking 等更轻量的替代方案。

优化不是一蹴而就的，持续关注体积变化，才能让小程序保持“轻快”的体验。
