虚拟 DOM 与 Diff 算法

虚拟 DOM 与 Diff 算法

引言

在现代前端框架中，虚拟 DOM 与 Diff 算法是一对密不可分的核心概念。它们共同支撑起了 React、Vue 等框架的声明式编程模型，让开发者从繁琐的手动 DOM 操作中解放出来。本文将从虚拟 DOM 的本质出发，逐步深入到 Diff 算法的实现细节，并对比 React 与 Vue 3 在这一领域的两种不同设计思路。

一、虚拟 DOM 是什么

虚拟 DOM 本质上是用 JavaScript 对象来描述真实 DOM 结构的一棵树。

真实 DOM：

对应的虚拟 DOM：

它就是一个普通的 JS 对象。操作它比操作真实 DOM 便宜得多，因为真实 DOM 节点包含大量属性、方法和事件，创建和修改成本都很高，每次修改还可能触发样式计算、布局和重绘。

虚拟 DOM 的核心思路是：先在内存里用 JS 对象算清楚”哪里变了”，再一次性、最小化地更新真实 DOM。

二、为什么需要虚拟 DOM

直接操作真实 DOM 有三个问题：

  1. 真实 DOM 很”重”：一个 DOM 节点背后是庞大的对象结构。
  2. 频繁操作性能差：每次修改都可能触发 reflow 和 repaint。
  3. 手动优化困难：开发者要自己判断哪里该改、怎么批量改，心智负担大。

虚拟 DOM 带来的价值不只是”快”，更重要的是让开发者用声明式的方式写 UI——你只需要描述”UI 应该是什么样”，框架负责算出”怎么改”。同时，虚拟 DOM 还带来了跨平台能力：同一棵虚拟 DOM 树可以渲染到 Web、Native、Canvas 等不同目标。

三、Diff 算法：虚拟 DOM 的大脑

虚拟 DOM 初次渲染时，会生成真实 DOM 并挂载到页面。当状态变化时，会生成一棵新的虚拟 DOM 树，然后通过 Diff 算法对比新旧两棵树，找出差异，只把变化的部分更新到真实 DOM。

完整对比两棵树的复杂度是 O(n³)，对前端来说太慢。因此框架都采用了启发式优化，把复杂度降到 O(n)，主要基于三条假设：

  1. 同层比较：只比较同一层级的节点，不跨层移动。
  2. 类型不同直接替换：节点 tag 不一样，就整棵子树删掉重建。
  3. 用 key 标识节点：列表渲染时通过 key 判断哪个节点是同一个，从而复用。

其中，列表 Diff 是最复杂、也是最能体现算法差异的部分。React 和 Vue 3 在这里走上了两条不同的路。

四、React：单向链表的”从左到右”

React 的 Diff 算法深度绑定了它的 Fiber 架构。

数据结构：没有”回头路”的单向链表

React 在内存中把虚拟 DOM 树重构成了 Fiber 链表。每个节点通过 child、sibling、return 三个指针连接。关键在于，它没有记录前一个兄弟节点的指针。因此当 Diff 算法走到某个位置时，只能继续往右看，无法轻易”回头”。

比较策略：左对齐 + Map 查找

正因为单向链表的限制，React 在处理列表更新时采用”从左向右依次对比”的策略：

  1. 先进行第一轮遍历，拿新旧列表的第一个、第二个……依次对比。
  2. 一旦遇到 key 或 type 对不上，第一轮遍历立即结束。
  3. 把剩下的旧节点全部丢进一个 Map（以 key 为键）。
  4. 拿着剩下的新节点去 Map 里查找能复用的旧节点。

React 用一个 lastPlacedIndex 变量记录”上一个被复用节点在旧列表中的索引”。遍历新列表时：

  • 如果当前节点在旧列表中的索引 ≥ lastPlacedIndex，说明相对顺序没变，不需要移动。
  • 如果小于 lastPlacedIndex，说明这个节点往后移了，标记为需要移动。

这是一种贪心近似策略——它能快速判断哪些节点”大概率不用动”，但无法保证移动次数最少。

代价与收益

这种策略在处理”节点从后面移到前面”的场景时比较吃力，会把中间的节点依次向后搬。但它换来了 Fiber 可中断渲染的能力：渲染工作可以被拆分成小块，随时暂停、恢复，从而避免长时间阻塞主线程。

五、Vue 3：双端指针的”两头夹击”

Vue 3 的 Diff 采用了更经典的双端对比策略。

比较策略：头尾指针同时收缩

Vue 3 在处理列表 Diff 时，会在新旧列表的两端分别设置指针，依次尝试四种匹配：

  1. 旧头 vs 新头：相同则复用，双头指针后移。
  2. 旧尾 vs 新尾：相同则复用，双尾指针前移。
  3. 旧头 vs 新尾：相同则复用，旧头后移、新尾前移。
  4. 旧尾 vs 新头：相同则复用，旧尾前移、新头后移。

这种”两头夹击”的方式，能非常高效地处理”尾部新增”、”头部插入”等常见场景，很快就能把两端相同的部分消化掉。

乱序处理：最长递增子序列

当两端指针交错，剩下的就是完全乱序的”硬骨头”。此时 Vue 3 会：

  1. 以新列表剩余部分为基准，建立 key → 新索引 的 Map。
  2. 遍历旧列表剩余部分，得到每个节点在新列表中的索引，组成一个数组。
  3. 计算这个数组的最长递增子序列（LIS）。

LIS 的含义是：这些递增的索引对应的节点，在旧列表里本来就是按顺序排好的，不需要移动。我们只要保持它们不动，把其他节点插进去就行。

最长递增子序列算法

Vue 3 源码里的函数叫 getSequence，用的是贪心 + 二分查找 + 回溯，时间复杂度 O(n log n)。

以数组 [0, 2, 3, 1, 4] 为例：

核心思路：维护一个数组 result，记录”长度为 i 的递增子序列，末尾元素的最小值”对应的原数组索引。同时用 p 数组记录每个元素的前驱，方便最后回溯。

逐步模拟：

  • i=0，值 0：result = [0]
  • i=1，值 2：2 > 0，追加，result = [0, 1]
  • i=2，值 3：3 > 2，追加，result = [0, 1, 2]
  • i=3，值 1：找到第一个 ≥ 1 的位置（索引 1，值 2），替换，result = [0, 3, 2]，p[3] = 0
  • i=4，值 4：4 > 3，追加，result = [0, 3, 2, 4]，p[4] = 2

回溯：从 result 最后一项索引 4 开始，顺着 p 往前找：4 → 2 → 1 → 0，倒过来就是 [0, 1, 2, 4]。

验证：原数组 [0, 2, 3, 1, 4]，取索引 0、1、2、4 → [0, 2, 3, 4]，确实是递增的，长度 4，正确。

回到 DOM 操作：有了 LIS [0, 1, 2, 4]，Vue 就知道这些节点不需要移动，剩下的节点需要插入到正确位置。这样 DOM 移动次数就被压到了最低。

为什么用贪心 + 二分

暴力找 LIS 是 O(n²)。Vue 3 用贪心策略——尽量让每个长度的子序列末尾元素越小越好，这样后面更容易接上——配合二分查找快速定位替换位置，把复杂度降到 O(n log n)。对于可能几百上千条数据的列表渲染，这个优化很关键。

六、LIS 的适用边界

需要澄清的是，LIS 只用在”带 key 的列表 Diff”里，而且是列表 Diff 的最后一个兜底步骤。
只有当双端对比卡住——四种比较全部失败，无法再靠两端匹配消化任何节点时，才会跳出双端循环，进入乱序处理，也才轮到 LIS 登场。

对于普通嵌套结构：

这是两个同层兄弟节点，但没有 key，也没有顺序变化。Diff 走的是普通的同层比较——按位置逐个比对，相同就复用，不同就替换，根本不会用到 LIS。

即使加上 key，只要顺序不变，也不会触发 LIS。只有顺序变了，才会进入带 key 的列表 Diff，进而可能用到 LIS。

场景 是否用 LIS
普通嵌套结构、静态兄弟节点 否
列表顺序不变，只增删尾部/头部 否（双端对比就解决）
列表顺序打乱，需要决定谁移动 是

七、一个完整的例子

假设旧列表 [A, B, C, D, E]，新列表 [A, C, D, B, E]，变化是 B 从第 2 位移到第 4 位。

Vue 3 的双端对比：

双端对比的每一轮，都按 旧头vs新头 → 旧尾vs新尾 → 旧头vs新尾 → 旧尾vs新头 的顺序依次尝试，命中一个就进入下一轮。

全程没有任何一轮出现”四种比较全失败”的情况，所以这次 Diff 不会进入 LIS 阶段。最终只需要移动 B 一个节点。

React 的处理：

  • 旧 A vs 新 A → 相同，继续
  • 旧 B vs 新 C → key 不同，第一轮结束
  • 建立旧节点 Map { b, c, d, e }
  • 遍历新列表剩余部分，用 lastPlacedIndex 判断：
    • C：旧索引 2，lastPlacedIndex = 2
    • D：旧索引 3 > 2，lastPlacedIndex = 3
    • B：旧索引 1 < 3 → 标记移动
    • E：旧索引 4 > 3，lastPlacedIndex = 4

最终也是移动 B 一个节点。

这个例子里两者结果相同。但在**”大部分有序、少量乱序”**的复杂场景下，Vue 3 的 LIS 能精确找出”最小移动集合”，而 React 的 lastPlacedIndex 是一种贪心近似，可能多移动一些节点。

八、两种设计的对比

维度 Vue 3 React
列表 Diff 策略 双端对比 + Map + LIS 从左到右 + Map + lastPlacedIndex
底层结构 虚拟节点数组，可自由设置头尾指针 Fiber 单向链表，不可反向遍历
头部插入 双端识别，1 次操作 需移动后续节点
尾部插入 双端识别，1 次操作 直接追加，1 次操作
中间移动 LIS 精确求最小移动集 贪心近似，可能多移
可中断 同步，不可中断 Fiber 可中断渲染
设计取舍 追求 Diff 精度 追求渲染调度能力

九、虚拟 DOM 的争议与未来

虚拟 DOM 并非没有争议。它的额外开销是真实存在的：维护 VNode 树、跑 Diff，都需要内存和计算成本。如果开发者精确知道要改哪个 DOM，直接改反而更快。

现代框架也在不断改进：

  • Vue 3 通过编译时优化（静态提升、Patch Flag）减少运行时 Diff 的工作量。
  • Svelte 在编译期直接生成 DOM 操作代码，完全绕过了虚拟 DOM。
  • SolidJS 采用细粒度响应式，状态变化直接定位到具体 DOM 节点。

这些方案都在某种程度上”绕过”或弱化了虚拟 DOM。但虚拟 DOM 的核心价值——让开发者用声明式的方式写 UI，同时保持可接受的性能——在可预见的未来依然是主流框架的基石。

十、结语

虚拟 DOM 与 Diff 算法，一个负责”描述 UI”，一个负责”算出最小变更”。它们共同构成了现代前端框架的运行时核心。

React 选择了 Fiber 单向链表 + 贪心 Diff，牺牲部分 Diff 精度，换来了可中断渲染的调度能力；Vue 3 选择了双端对比 + LIS，追求 Diff 的精确性和最小移动。

两种设计没有绝对的优劣，它们只是对”什么更重要”给出了不同的答案。理解它们背后的取舍，比记住”哪个更快”更有价值——因为技术选型从来不是比谁跑分高，而是看谁更契合你要解决的问题。
