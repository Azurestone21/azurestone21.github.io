Hooks 为什么不能条件调用

Hooks 的状态不是存在组件上，而是存在 Fiber 的 memoizedState 链表里。调用顺序就是“地址”。一旦条件调用导致顺序变化，React 就会把状态错配到别的 Hook 上。

一、Hooks 状态存在哪

函数组件本身没有实例，useState 返回的 state 不能存在函数里，因为函数每次 render 都会重新执行，局部变量会丢失。

  • 第一个 useState → 取 Hook1，拿到 a 的状态和更新队列。
  • 第二个 useState → 取 Hook2，拿到 b。

所以：第 N 个 Hook 的状态，永远存在链表的第 N 个节点上。

假设写了条件调用：

第一次 render，isLoggedIn = true

调用顺序变成：

React 按顺序取：

  • 第 1 个 useState → 取 Hook1，拿到 name。✅ 正确。
  • 第 2 个 useState → 取 Hook2，但 Hook2 存的是 age 的状态 18。❌
    • count 拿到了 18。
    • setCount 拿到的是 setAge 的更新队列。

于是：

  • count 初始值变成了 18。
  • 调用 setCount 实际会去改 age 的状态。
  • age 这个 Hook 被“跳过”后，后面的 Hook 全部错位。

这就是状态错配。

四、更严重的后果

1. 状态错乱

如上，count 拿到了 age 的状态。

2. 更新队列错配

setCount 实际是 setAge，调用后更新的是 age 的队列，而 age 已经不在链表里，行为不可预期。

3. Hook 数量不匹配时报错

如果第二次 render 的 Hook 数量比第一次少，React 遍历到链表末尾时找不到对应 Hook，会抛错：

这是 React 的一种保护机制，但即使数量相同、顺序不同，也不会报错，只会静默错配，更难排查。

4. 依赖 Hook 顺序的 API 全受影响

useEffect、useMemo、useCallback、useRef、useContext 全都依赖链表顺序。一个 Hook 错位，后面全乱。

五、为什么 React 不设计成按名字或 key 识别

理论上可以给每个 Hook 一个名字或 key，用 Map 存储：

但 React 没这么做，原因：

  1. 性能：链表 + 顺序访问是 O(1) 且无哈希开销，Map 查找更慢。
  2. 体积：不需要为每个 Hook 分配 key，减少内存。
  3. 语法简洁：不需要用户写 useState('name', ...) 这种冗余参数。
  4. 编译期无法静态确定顺序：React 运行时才能确定调用顺序，用顺序是最自然的方案。
  5. 约定优于配置：只要遵守“顶层调用”，顺序就稳定，不需要额外机制。

代价就是：必须保证每次 render 的 Hook 调用顺序完全一致。

七、和 Fiber 的关系

  • Fiber 节点保存 memoizedState，就是 Hooks 链表。
  • 函数组件每次 render，React 从 fiber.memoizedState 开始，按顺序遍历链表。
  • 链表节点和 Hook 调用一一对应，顺序是唯一映射。

所以：

Hooks 的“状态”不在函数里，而在 Fiber 的链表里；调用顺序就是访问链表的“指针”。条件调用会打乱顺序，导致指针指向错误的节点。

这也解释了为什么：

  • Hooks 只能在函数组件或自定义 Hook 顶层调用。
  • 自定义 Hook 必须以 use 开头（约定，便于 lint 检查）。
  • ESLint 的 react-hooks/rules-of-hooks 能静态检测违规。

八、总结

Hooks 的状态存在 Fiber 的 memoizedState 链表上，React 靠调用顺序访问链表。条件调用会让顺序变化，导致状态错配到别的 Hook 上，所以 Hooks 必须无条件和稳定地按同一顺序调用。
