Taro 长列表渲染

Taro 长列表渲染

一、 核心痛点总览

小程序长列表卡顿的根源在于 逻辑层 ↔ 渲染层 的异步通讯机制（setData）。

  • 通讯瓶颈：数据序列化与传输耗时。
  • 内存瓶颈：DOM 节点过多导致渲染树庞大。
  • 交互瓶颈：图片加载导致布局抖动（CLS）。

二、 第一层：数据通信与渲染优化（基础必答）

优化维度 核心策略 关键原理解析
数据裁剪 过滤冗余字段 接口数据往往包含几十个字段，只保留 id、title、pic 等渲染必需的字段，减小 setData 体积。
分页加载 20-30 条/页 控制单次渲染节点数。
setData 限制 单次 < 1MB 微信小程序单次传输数据超过 1MB 会直接崩溃或报错。
图片懒加载 lazy-load 仅加载可视区及预加载区图片，减少并发网络请求和 GPU 渲染压力。

三、 第二层：交互体验与预加载（消除白屏）

痛点：滑动到底部时才请求下一页，网络慢导致“加载中”闪烁。

核心解法：预加载阈值

  • 监听 onScrollToLower 或滚动事件，计算 剩余高度。
  • 触发时机：当剩余可视高度小于 2-3 屏 时，提前发起下一页请求。
  • 滚动计算标准：scrollTop + clientHeight >= scrollHeight - threshold。

辅助策略：

  • 骨架屏：数据未返回时展示占位灰块，比转圈 Loading 视觉上更平滑。
  • 请求锁：使用 useRef 做 isLoading 标记，防止预加载和触底加载同时发起两次请求。

四、 第三层：布局稳定性与图片防抖（防跳动）

痛点：图片加载前后高度变化（0 -> 真实高度），导致滚动条跳动，用户点错位置。

🅰️ 方案一：CSS 占位（强力推荐）

利用 aspect-ratio 提前锁定容器宽高比，图片加载前后容器尺寸纹丝不动。

🅱️ 方案二：后端返回宽高（工业级标准）

后端接口附带 picWidth / picHeight，前端根据屏幕宽度动态计算容器高度（行内样式写死），保证 object-fit: contain（完整显示）时不跳动。

🅲️ 方案三：小程序 widthFix 的坑

  • 现象：mode="widthFix" 在 onLoad 后才调整高度，依然会触发重排。
  • 补救：在外层包裹固定比例的 aspect-ratio 父容器，或将 min-height 设为预估高度。

五、 第四层：虚拟列表底层原理（深水区）

适用场景：数据量突破 1000+ 条，即使分页也积累了过多 DOM 节点。

1. 核心机制

只渲染 可视区域（Viewport） + 上下缓冲区（Buffer） 内的节点。

2. 定高 vs 不定高

类型 实现原理 复杂度
定高 startIndex = scrollTop / itemHeight，直接计算偏移量。 低
不定高 必须采用 “预估-渲染-测量-修正” 闭环。 高

3. 不定高标准推导逻辑（面试必背）

  1. 预估（Estimate）：先假设每项高度为 200px（默认值），用于计算滚动条总高度和初始偏移量（translateY），保证页面能滑得动。
  2. 渲染（Render）：渲染可视区域内的 Item。
  3. 测量（Measure）：渲染完成后，通过 createSelectorQuery 精确获取每一项的真实高度。
  4. 修正（Correct）：将真实高度存入 高度缓存池（Map），并重新计算总高度和当前偏移量。
  5. 为什么必须预估？ 因为 JS 逻辑层在渲染前无法获知 DOM 真实高度（特别是涉及图片异步加载时），必须给一个初始值让滚动容器先“撑起来”。

4. 工程化落地路径

  • 路径 A（新能力）：微信小程序 Skyline 渲染引擎 的 ListBuilder 组件，设置 type="dynamic" 原生支持不定高，性能最优（仅限微信）。
  • 路径 B（社区方案）：使用 taro3-virtual-list 等库，它们通过骨架屏测量法更好地解决了白屏问题。

六、 第五层：架构设计与状态恢复（压轴题）

面试场景：用户从列表页 -> 详情页 -> 返回列表页。

关键认知（必读）

在标准小程序中，navigateTo + navigateBack 不会销毁页面实例，滚动位置是原生保留的。
所以我们的重点不是“恢复滚动”，而是防止 onShow 里的冗余请求破坏体验，以及处理 redirectTo 等销毁场景。

1. 数据缓存策略（防刷新）

  • 核心机制：Stale-While-Revalidate（陈旧数据优先）。
  • 实现：
    • 在全局 Store（Redux/Zustand）中存储列表数据 + timestamp（时间戳）。
    • onShow 时判断：若缓存存在且未过期（如 < 5分钟），直接展示缓存，不发请求。
    • 若过期，先展示旧数据（防白屏），后台静默请求新数据，请求成功后增量合并（patch），不重置整个数组。

2. 滚动位置兜底（针对 redirectTo/reLaunch）

  • 存：在 onUnload 中读取 scrollTop 存入内存。
  • 还：在 onLoad 中通过 ScrollView 的 scroll-top 属性还原。
  • ⚠️ 关键重置技巧（防不生效）：必须先置 0，再 nextTick 置目标值，强制触发渲染层更新。

3. 跨页面状态同步（详情页修改了数据）

  • 详情页操作（如收藏/删除）成功后，通过 EventBus 或 直接 dispatch Redux Action 通知列表页。
  • 列表页收到信号后，精确修改（patch） 对应 ID 的单项数据（如 list[5].isFav = true），绝不重建整个数组。

4. 分页状态持久化

  • 不仅要存 list，还要存 pageIndex（当前页码）和 hasMore（是否还有更多）。
  • 返回后触底加载，直接从 pageIndex + 1 开始请求。

🎯 总结

“处理长列表，我们要分层治理：**首屏用分页和裁剪减轻 setData 压力；交互上用预加载消除白屏；视觉上用 aspect-ratio 锁住布局跳动；极致场景引入虚拟列表，通过预估-测量闭环解决不定高痛点；最后在架构上，利用小程序的页面栈特性，配合缓存时间戳和精准 Patch 更新，实现返回‘零请求、瞬开、无闪烁’的极致体验。”
