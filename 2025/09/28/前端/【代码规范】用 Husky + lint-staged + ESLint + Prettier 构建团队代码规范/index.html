用 Husky + lint-staged + ESLint + Prettier 构建团队代码规范

代码规范的核心矛盾在于：规则必须统一，但执行必须无感。如果每次提交都靠人工记得跑 lint 和 format，规范注定会失效。真正可靠的方案是让工具链在 git commit 时自动完成检查与修复，开发者的肌肉记忆不需要改变。

  • ESLint 负责代码质量，检查未使用变量、潜在 bug、危险写法。
  • Prettier 负责代码格式，统一缩进、引号、换行风格。
  • Husky 负责触发时机，在 pre-commit 阶段自动执行检查。
  • lint-staged 负责执行范围，只检查本次提交涉及的文件，避免全量 lint 导致的性能问题。

集成 ESLint 与 Prettier：消除冲突

这是整套工具链中最关键的一步。ESLint 和 Prettier 各自都包含一些格式相关的规则，如果不做处理，两者可能对同一段代码给出矛盾的要求，导致自动修复互相覆盖。

解决方案是使用 eslint-config-prettier，它会关闭所有与 Prettier 冲突的 ESLint 规则，让 Prettier 独占格式化职责。

配置完成后，ESLint 只负责“代码写得对不对”，Prettier 只负责“代码排得齐不齐”，两者各司其职。

预期结果：

  1. Husky 触发 .husky/pre-commit
  2. lint-staged 筛选出暂存的 JS 文件
  3. ESLint 自动修复质量问题（如果可修复）
  4. Prettier 自动重写格式
  5. 修复后的文件被重新暂存
  6. 提交完成

如果 ESLint 遇到无法自动修复的问题（比如未使用变量），提交会被阻止，终端会显示具体的错误信息，开发者修复后重新提交即可。

最佳实践与注意事项

不要在 pre-commit 中跑全量检查。 全量 lint 在稍大的项目中可能需要数秒甚至更久，开发者会因为等待而使用 git commit --no-verify 绕过检查，规范就形同虚设。lint-staged 的价值正是把检查范围缩小到暂存文件，保持提交速度在可接受范围内。

关键检查要在 CI 中兜底。 pre-commit 钩子可以被 --no-verify 绕过，也可以被开发者不安装 Husky 而跳过。类型检查、单元测试、安全扫描这类不能妥协的检查，必须在 CI 流水线中再跑一遍。

eslint-config-prettier 的位置不能错。 在 Flat Config 中，它必须放在配置数组的最后，否则它关闭的规则会被后面的配置重新启用。

定期更新工具版本。 lint-staged v16 要求 Node.js 20.18+，v17 要求 Node.js 22+。Husky v9 不再使用 husky install 命令，而是 husky init。保持工具链更新可以减少兼容性问题。

提交信息规范可以一并纳入。 如果团队使用 Conventional Commits，可以再加一个 commit-msg 钩子配合 commitlint，但这不属于本文核心链路，按需扩展即可。

总结

这套工具链的本质是 职责分离：ESLint 管质量，Prettier 管格式，lint-staged 管范围，Husky 管时机。每个工具只做一件事，通过清晰的边界组合在一起。配置一次之后，开发者的日常操作没有任何变化，但代码库的质量底线被自动守住。

唯一需要团队约定的事情是：代码规范不是靠自觉，是靠自动化。
