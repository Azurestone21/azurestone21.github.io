【React】深入理解 React Fiber

深入理解 React Fiber：可中断渲染、双缓存与 Commit 阶段

本文从 Fiber 的数据结构讲起，串联节点生成、双缓存、两阶段渲染、flags 副作用标记，以及真实 DOM 的修改时机，帮你建立一套完整的 Fiber 心智模型。

React 16 引入 Fiber 之前，React 的协调器是 Stack Reconciler。它递归遍历虚拟 DOM，整个过程同步且不可中断。一旦更新开始，主线程就会被一直占用，组件树稍微大一点，页面就容易卡顿、输入延迟。

Fiber 的出现就是为了解决这个问题：把大任务拆成小任务，让更新能暂停、能恢复、能按优先级执行。

一、Fiber 是什么

Fiber 不只是一个数据结构，它包含三层含义：

  1. 数据结构：每个 React Element 对应一个 Fiber 节点，用链表连接成树。
  2. 工作单元：每个 Fiber 节点是一个可执行、可中断的工作单元。
  3. 调度架构：配合 Scheduler 和 Lane 优先级模型，让更新可中断、可恢复、可插队。

React 15 及以前用递归同步执行，问题很明显：

  • 递归调用栈一旦开始，不能中断；
  • 组件树深时，render 长时间占用主线程；
  • 浏览器页面卡顿、输入延迟，导致掉帧；
  • 高优先级更新无法插队。

Fiber 的目标就是：把大任务拆成小任务，能暂停、能恢复、能按优先级执行。

Fiber 与 React Element 的区别

维度 React Element Fiber
本质 不可变的 UI 描述 可变的工作单元 + 状态容器
生命周期 每次 render 重新创建 可复用，跨多次 render 存在
内容 type、props、key 状态、副作用、优先级、DOM 引用、链表指针
作用 描述“UI 应该是什么样” 决定“怎么更新、何时更新”

React Element 只是描述，不能调度、不能保存状态、不能标记副作用。Fiber 才是真正参与更新流程的工作单元。

四、flags 与 subtreeFlags

flags 是什么

flags 是 Render 阶段给 Commit 阶段留下的施工清单。

Render 阶段只负责标记“哪些节点要做什么操作”，Commit 阶段才根据 flags 去真正执行 DOM 操作。

常见 flags：

flag 含义 Commit 阶段的操作
Placement 新节点插入，或节点移动 appendChild / insertBefore
Update 属性或文本更新 更新 DOM 属性 / 文本
Deletion 节点删除 removeChild，卸载组件
ChildDeletion 子节点删除 处理deletions 数组
Passive useEffect 需要执行 异步调度flushPassiveEffects
Layout useLayoutEffect 需要执行 Layout 阶段同步执行
Ref ref 需要更新 Layout 阶段绑定/解绑 ref
Snapshot getSnapshotBeforeUpdate Before Mutation 阶段执行

为什么用 flags 而不是 effect list

React 17 之前用 effect list，把所有有副作用的 Fiber 串成链表，Commit 阶段只遍历这个链表。缺点是：

  • 需要额外维护链表指针；
  • 并发模式下难以处理中断和重建；
  • 无法高效支持 subtreeFlags 的跳过优化。

React 17 之后改用 flags + subtreeFlags：

  • 信息直接挂在 Fiber 上，不需要额外链表；
  • 可以配合 subtreeFlags 跳过无副作用子树；
  • 更适合并发模式的中断和恢复。

  • current 树：屏幕上正在显示的 UI。
  • workInProgress 树：内存中正在构建的新 UI。

两棵树的对应节点通过 alternate 互相指向。

首次渲染只有 WIP 树被完整构建，current 树只是一个空根节点；Commit 交换后，WIP 树才成为完整的 current 树，双缓存从下一次更新才开始真正交替复用。

首次渲染后，备用的 WIP 树只有根节点

首次渲染 Commit 后：

  • current 树：完整组件树。
  • 备用的 WIP 树：只有根节点，没有子节点。

因为首次渲染时，current 树从未被完整构建过。初始的 current 树只是一个占位的 HostRootFiber。Render 阶段所有子节点都新建在 WIP 树上，没有对应的 current 子节点可以复用。所以旧 current 树自然没有子节点。

第一次更新时，React 从新的 root.current（完整树）出发：

  • 根节点：current.alternate 已存在，直接复用。
  • 子节点：current.child.alternate === null，走新建分支，创建 WIP 子节点并建立 alternate。

从第二次更新开始，子节点的 alternate 都已存在，才真正进入“两棵完整树交替复用”的状态。

六、每次渲染都会重新构建 WIP 吗

答案是分层的：

每次更新都会进入 Render 阶段，都会从 root.current 出发构建 WIP 树。但“构建”不等于“全部新建”——绝大多数节点是复用 alternate 的。

WIP 节点的“一样”和“不一样”

WIP 节点确实从 current 克隆了很多东西，但关键字段不一样：

字段 current Fiber WIP Fiber
memoizedProps 上次渲染的 props 保留旧值，供对比
pendingProps —— 新的 props
memoizedState 上次的 state 保留旧值
updateQueue 旧更新队列 新的更新队列
child 旧子节点 先复制，再被 diff 结果覆盖
flags 旧的副作用标记 重置为 NoFlags，重新标记
alternate 指向 WIP 指向 current

“一样”指的是 Fiber 节点的树形结构、type、key、stateNode 这些身份信息。
“不一样”指的是 pendingProps、updateQueue、flags、memoizedState 这些会因为新更新而变化的数据。

WIP 节点的“壳”是从 current 克隆的，但“内容”来自新的 render 结果。diff 不是两棵 Fiber 树对比，而是新的 ReactElement 和 current 子 Fiber 对比。WIP 树是 diff 的产物，不是 diff 的输入。

九、两阶段渲染

整体流程

Render 阶段

核心任务：构建 workInProgress 树，做 diff，打 flags。不碰真实 DOM。

工作循环：

  • beginWork：处理当前 Fiber，执行组件 render，diff 子节点。
  • completeWork：创建/更新 DOM 实例，把子 DOM 挂到父 DOM 下，向上冒泡 subtreeFlags。
  • 每处理完一个 Fiber，检查 shouldYield()，时间片用完就暂停。

注意：completeWork 里会调用 createInstance 创建 DOM 实例，但不挂载到页面，只是存在于内存中，挂在 Fiber 的 stateNode 上。

Commit 阶段

核心任务：根据 flags 真正操作真实 DOM，同步不可中断。

三个子阶段：

子阶段 做什么
before mutation getSnapshotBeforeUpdate
mutation DOM 增删改移，componentWillUnmount，清理 ref
layout componentDidMount、componentDidUpdate、useLayoutEffect、绑定 ref

完成后：

useEffect 在 commit 后异步调度，不阻塞浏览器绘制。

十、真实 DOM 到底在哪个阶段修改

一个常见误解：completeWork 里创建了 DOM，是不是就改了真实 DOM？

不是。

  • Render 阶段：completeWork 调用 createInstance 创建 DOM 实例，但不挂载。它只是内存中的实例，不在文档里。
  • Commit 阶段：真正修改真实 DOM。

Commit 三个子阶段的 DOM 操作：

子阶段 DOM 操作
before mutation 不碰 DOM
mutation commitPlacement 插入、commitWork 更新、commitDeletion 删除
layout DOM 已改完，执行生命周期、ref

为什么这样设计？

因为 Render 阶段可能被暂停、恢复、甚至丢弃重来。如果在这个阶段改真实 DOM，一旦任务被中断或丢弃，页面就会处于不一致的中间状态，用户会看到闪烁或错乱。

Commit 阶段同步、一气呵成，只有在这里改 DOM，才能保证用户看到的是要么旧状态，要么新状态，不会看到中间态。

为什么 render 可中断，commit 不可中断

维度 render commit
做什么 计算、diff、打 flags 操作真实 DOM、执行生命周期
是否碰 DOM 不碰 碰
能否中断 能 不能
中断后果 丢弃 WIP，重新 render UI 不一致、状态错乱、无法回滚
本质 草稿，可重来 发布，必须原子

render 只算不改，算错可重来；commit 要改真实 DOM，改到一半无法回滚，必须一次性保证 UI 一致。

十二、常见问题

Fiber 节点怎么生成？
Render 阶段 beginWork 中，由 createFiberFromElement / useFiber 创建或复用。

每次渲染都会重新构建 WIP 吗？
每次更新都会进入 Render 阶段并尝试构建 WIP，但大部分节点通过 alternate 复用，只有新增、无法复用的节点才新建。bailout 会跳过无更新的子树。

更新时 WIP 是根据 current 创建的吗？怎么 diff？
WIP 的“壳”从 current 克隆，但“内容”来自新的 render 结果。diff 是新的 ReactElement 和 current 子 Fiber 对比，不是两棵 Fiber 树对比。WIP 树是 diff 的产物。

第一次更新时 alternate 怎么建立？
在 reconcileChildren → reconcileSingleElement → useFiber → createWorkInProgress 中，因为 current.alternate === null，走新建分支，创建 WIP 副本，复制状态，然后手动建立双向指向。

真实 DOM 何时修改？
Commit 阶段的 Mutation 子阶段。

completeWork 创建的 DOM 挂载了吗？
没有，只是内存中的实例，Mutation 阶段才挂载。

current 和 WIP 如何切换？
root.current = finishedWork。

交换后 alternate 要处理吗？
不用，alternate 是对称无方向的，始终互相指向。

首次渲染是两棵树吗？
不是，current 树只有根节点，WIP 树逐层构建。首次渲染后，备用的 WIP 树只有根节点，没有子节点。

子节点什么时候有 alternate？
第一次更新时建立。

双缓存什么时候真正生效？
从第二次更新开始，两棵完整树交替复用。

flags 有什么用？
Render 阶段给 Commit 阶段留的施工清单，标记哪些节点要插入、更新、删除。subtreeFlags 用于快速跳过无副作用的子树。

为什么 render 可中断？
链表遍历 + 全局 workInProgress + shouldYield。

为什么 commit 不可中断？
改真实 DOM 无法回滚，必须原子。

十三、总结

Fiber 把渲染拆成可中断的工作单元。

Render 阶段只算不改，在内存中构建 WIP 树，通过 diff 新的 ReactElement 和 current 子 Fiber 决定复用还是新建，并打上 flags；Commit 阶段同步改真实 DOM，根据 flags 执行对应操作，最后交换 root.current，让 WIP 树成为新的 current 树。

两棵树通过 alternate 双向指向，交替复用。首次渲染只完整构建一棵树，第一次更新为子节点建立 alternate，第二次更新起才真正双树交替。

理解这条主线，再去看 React 的并发特性、Suspense、useTransition，就会清晰很多。
