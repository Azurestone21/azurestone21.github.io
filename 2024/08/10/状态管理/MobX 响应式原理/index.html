MobX 响应式机制与依赖收集

MobX 响应式机制与依赖收集

一句话概括：MobX 的响应式系统是一个基于 Proxy 数据劫持的发布-订阅模型，通过全局执行上下文在运行时自动收集依赖，实现精确到属性级的变更通知，并利用批量异步更新最大化性能。

1. 响应式的核心三要素

MobX 的响应式系统由三类角色协作完成：

flowchart LR
    subgraph Observable["① Observable（被观察者）"]
        O1[可观察数据]
        O2[内部维护 observers 列表]
    end

    subgraph Reaction["② Reaction（观察者）"]
        R1[autorun / reaction / when]
        R2[observer 组件]
        R3[computed 计算值]
    end

    subgraph Derivation["③ Derivation（派生）"]
        D1[computed 值]
        D2[既是观察者也是被观察者]
    end

    Observable -->|读取时建立连接| Reaction
    Reaction -->|修改时通知| Observable
    Observable -->|依赖变化时| Derivation
    Derivation -->|被读取时| Reaction
角色 说明 示例
Observable（可观察数据） 被 Proxy 包装的数据，内部维护 observers 列表 observable({ count: 0 })
Reaction（观察者） 监听数据变化并执行副作用的函数 autorun, reaction, observer 组件
Derivation（派生值） 从状态计算出的值，既是观察者也是被观察者 computed getter

2. 依赖收集的完整流程

2.1 核心机制：全局执行上下文指针

MobX 依赖收集的精髓在于一个全局唯一的指针：globalState.trackingDerivation

  • 当 Reaction 执行时，MobX 将该 Reaction 放入这个指针。
  • 当 Observable 被读取时，检查这个指针，如果有值则建立连接。
  • 执行完毕后，立即将指针置空。
sequenceDiagram
    participant User as 开发者代码
    participant AR as autorun 实例
    participant Global as globalState.trackingDerivation
    participant Proxy as Observable Proxy (Getter)
    participant Obs as Observable.observers 列表

    User->>AR: ① 执行 autorun(() => { ... })
    AR->>Global: ② 入栈：trackingDerivation = 该 autorun

    Note over AR: ③ 开始执行回调函数

    AR->>Proxy: ④ 读取 store.count（触发 getter）
    Proxy->>Global: ⑤ 检查 trackingDerivation 是否为空？
    Global-->>Proxy: ⑥ 不为空，返回当前 autorun

    Proxy->>Obs: ⑦ 双向绑定：autorun 加入 observers 列表
    Obs-->>Proxy: ⑧ 绑定完成

    Proxy-->>AR: ⑨ 返回 count 的值

    Note over AR: ⑩ 回调函数执行完毕

    AR->>Global: ⑪ 出栈：trackingDerivation = null

    Note over Global: ✅ 依赖收集完成！仅追踪实际读取的属性

    section 执行中（1）

2.4 依赖的清理与重建

每次 Reaction 重新执行前，MobX 会：

  1. 清空旧依赖：遍历 dependencies，从每个 Observable 的 observers 中移除自己。
  2. 重新执行回调：在同步执行过程中，重新建立新的依赖连接。
执行状态 依赖列表 说明
第一次（isReady = false） [isReady] 只追踪 isReady
第二次（isReady = true） [isReady, data] data 被读取，加入追踪
第三次（isReady = false） [isReady] data 不再被读取，自动移除

3. Proxy 代理：响应式的技术根基

3.1 什么是 Proxy？

Proxy 是 ES6 提供的对象拦截器。对对象的所有操作（读取、修改、删除）都必须先经过 Proxy 的“门卫”函数。

3.2 MobX 为什么必须用 Proxy？

对比维度 Object.defineProperty（MobX 4/5） Proxy（MobX 6+）
新增属性 ❌ 无法拦截，需用 set 方法 ✅ 自动拦截
删除属性 ❌ 无法拦截 ✅ 可拦截 deleteProperty
数组操作 ❌ 需重写数组方法 ✅ 自动拦截索引和 length
性能 需遍历所有属性 懒代理，按需拦截

4.1 完整数据流全景图

flowchart TD
    Start[创建 observable 数据] --> AR[创建 autorun / observer 组件]
    AR --> Execute[执行回调函数]
    Execute --> Check{读取 observable 属性?}

    Check -->|是| Getter[触发 getter 拦截]
    Check -->|否| Done[执行完毕]

    Getter --> Global{trackingDerivation<br>是否有值?}

    Global -->|有| Bind[双向绑定:<br>属性.observers.add(观察者)<br>观察者.dependencies.add(属性)]
    Global -->|无| NoBind[不建立连接<br>仅返回值]

    Bind --> Continue[继续执行下一条语句]
    NoBind --> Continue
    Continue --> Check

    Done --> Clear[出栈: trackingDerivation = null]

    subgraph 变更阶段["--- 变更阶段（异步批量） ---"]
        Mutate[修改 observable 属性] --> Setter[触发 setter 拦截]

        Find --> Mark[标记观察者为"脏"]

        Schedule --> Batch[微任务执行：遍历队列]
        Batch --> React[观察者重新执行]
    end

5. 全局指针 trackingDerivation 详解

5.1 是什么？

globalState.trackingDerivation 是一个全局单例指针，指向当前正在执行的 Reaction 实例。

5.2 什么时候有值，什么时候为 null？

flowchart LR
    subgraph 有值["✅ trackingDerivation 不为 null"]
        A1[observer 组件渲染函数执行中]
        A2[autorun/reaction/when 回调执行中]
        A3[computed getter 执行中]
        A4[上述调用链中的 action]
    end

    subgraph 无值["❌ trackingDerivation 为 null（冷读取）"]
        B1[事件回调 onClick/onChange]
        B2[setTimeout/Promise.then/await 之后]
        B3[useEffect 直接读取（无 autorun）]
        B4[普通函数/工具函数]
        B5[action 内部（非 Reaction 调用链）]
    end

5.3 各场景追踪状态速查

场景 trackingDerivation 是否建立依赖
observer 组件的渲染函数 ✅ 指向组件 Reaction ✅ 是
autorun 回调函数同步部分 ✅ 指向自身 ✅ 是
computed getter 执行中 ✅ 指向自身 ✅ 是
事件回调（onClick/onChange） ❌ null ❌ 否
setTimeout 回调 ❌ null ❌ 否
Promise.then / await 之后 ❌ null ❌ 否
useEffect 直接读取（无 autorun） ❌ null ❌ 否
action 内部（非 Reaction 调用链） ❌ null ❌ 否

6. 依赖追踪失效场景

6.1 异步回调中的追踪中断

6.2 为什么异步回调中不能建立依赖？

  1. 防止幽灵依赖：异步回调执行时，原始的 autorun 早已执行完毕并出栈。
  2. 避免内存泄漏：如果异步回调建立了依赖，回调函数会被永久挂在 observers 列表中。
  3. 防止死循环：避免在 Action 中读取数据时意外建立依赖，导致修改时再次触发自身。

7. computed 的懒执行与挂起

7.1 状态机

stateDiagram-v2
    [*] --> 挂起_Suspended: 创建 computed，无观察者

    挂起_Suspended --> 追踪_Tracking: 被 autorun/组件 读取

    追踪_Tracking --> 最新_UpToDate: 依赖未变化，返回缓存

    最新_UpToDate --> 脏_Stale: 依赖的 observable 发生变化

    脏_Stale --> 追踪_Tracking: 被读取时重新计算

    追踪_Tracking --> 挂起_Suspended: 所有观察者销毁（observers 为空）

    note right of 挂起_Suspended
        不监听任何上游数据
        不占用内存资源
    end note

    note right of 追踪_Tracking
        有观察者在使用
        监听上游变化
        正常缓存
    end note

    note right of 脏_Stale
        缓存已失效
        等待下次读取时重新计算
    end note

7.2 有观察者 vs 无观察者

flowchart LR
    subgraph 有观察者["✅ 有观察者（在 autorun 内读取）"]
        A1[computed 被读取] --> A2[检查 observers 列表]
        A2 --> A3[有 autorun 在列表中]
        A3 --> A4[激活：监听上游变化]
        A4 --> A5[上游变化 → 缓存失效 → 重新计算]
        A5 --> A6[多次读取 → 直接返回缓存]
    end

    subgraph 无观察者["❌ 无观察者（在 autorun 外读取）"]
        B1[computed 被读取] --> B2[检查 observers 列表]
        B2 --> B3[列表为空]
        B3 --> B4[挂起：不监听上游]
        B4 --> B5[上游变化 → 不知道，无反应]
        B5 --> B6[多次读取 → 每次都重新计算]
    end

8.2 调试技巧

问题 调试方法

8.3 快速排查清单

现象 可能原因 解决方案
依赖变了，computed 不更新 依赖了非 observable 数据 将依赖转为 observable
每次读取都重新计算 无 Reaction 在使用 配置 keepAlive: true
组件无限重渲染 computed 返回新对象引用 返回原始值或配置深度比较
await 后的依赖不追踪 异步中断追踪 将异步逻辑移至 action
事件回调中读取不更新 非响应式上下文 在组件渲染函数或 autorun 中读取

9. 术语表

术语 说明
Observable 可观察数据，通过 Proxy 包装，内部维护 observers 列表
Reaction 观察者，如 autorun、reaction、observer 组件
Derivation 派生值，即 computed，既是观察者也是被观察者
trackingDerivation 全局指针，指向当前正在执行的 Reaction
observers 每个 Observable 内部维护的观察者列表
dependencies 每个 Reaction 内部维护的依赖列表
Proxy ES6 代理，MobX 用于拦截 get/set 操作
批量更新 MobX 通过事务 + 去重队列 + 微任务实现
懒执行 computed 只在被读取时计算
自动挂起 无观察者时 computed 自动取消上游监听

💡 记忆口诀

读取时收集依赖，修改时批量通知；
Proxy 拦截 get/set，微任务压扁更新；
computed 懒算又缓存，无观察者就挂起；
异步回调不追踪，action 里改状态。

核心就三句话：读时收集，改时通知，批量执行。
