MobX 多store联动

MobX 多store联动

在 MobX 中管理多个 Store 并让它们高效联动，最主流、最推荐的方式是 “Root Store 模式” 。

这个模式的核心思想是创建一个“根 Store”（Root Store），让它作为所有子 Store 的“中央调度室”，负责统一管理和协调它们之间的通信。

模式一：Root Store 模式（最推荐）

这是 MobX 官方社区最推崇的实践，主要包含以下三步：

1. 创建子 Store，并接收 rootStore 引用

每个子 Store 在构造函数中接收 rootStore 实例，并将其保存，以便需要时调用其他 Store 的方法。

2. 创建 Root Store，组装所有子 Store

Root Store 负责实例化所有子 Store，并将自身（this）作为参数传递给它们。

3. 在 UI 层注入与使用

创建好 Root Store 后，需要通过 React 的 Context API 或 mobx-react 的 Provider 将其注入到组件树中。

方式一：使用 mobx-react 的 Provider（较旧，但仍可用）

然后，在子组件中，可以通过 inject 装饰器或 useContext 来获取需要的 Store。

方式二：使用 React Context + Hooks（更现代）

除了“Root Store”模式，MobX 多 Store 联动还有几种常见的方式，各有其适用场景。下面为你详细展开。

方式二：Singleton 单例模式

这是最简单直接的方式，适合小型项目或工具类 Store。

核心做法：将 Store 实例化为单例并导出，其他模块直接导入使用。

✅ 优点：

  • 代码最少，无需额外的初始化或传递逻辑。
  • 在任何地方（组件、工具函数、其他 Store）都可以直接导入使用。

❌ 缺点：

  • 服务端渲染（SSR）问题：Node.js 中模块只初始化一次，单例状态会被所有用户共享，导致数据串扰。
  • 单元测试困难：状态在测试用例间共享，需要手动重置。
  • 耦合度高：Store 之间直接依赖，难以替换或 mock。

适用场景：纯客户端应用、小型项目、或不需要测试的工具类 Store。

方式三：方法级依赖注入（参数传递）

这是一种更灵活、临时性的联动方式：不保存引用，只在调用时把依赖的 Store 实例作为参数传进去。

✅ 优点：

  • 解耦：Store 之间不保存长期引用，依赖关系显式且临时。
  • 测试友好：可以轻松传入 mock 对象。

❌ 缺点：

  • 需要手动在调用链中层层传递，代码冗余。
  • 不适合频繁、多处调用的场景。

适用场景：初始化逻辑、一次性操作、或需要最小化耦合的地方。

方式四：使用 reaction 进行响应式联动

这是一种“数据驱动”的联动方式：在一个 Store 中监听另一个 Store 的 observable 变化，并自动触发响应。

✅ 优点：

  • 声明式：逻辑清晰，自动响应变化。
  • 解耦：通过 reaction 隔离了直接的方法调用。

❌ 缺点：

  • 需要手动管理 reaction 的生命周期（如组件卸载时 dispose）。
  • 过度使用会使数据流变得隐晦，难以追踪。

适用场景：当一个 Store 的状态需要自动、持续地同步到另一个 Store 时。

方式五：使用 mobx-state-tree (MST)

mobx-state-tree 是 MobX 官方提供的结构化状态管理库，它提供了更严格的架构和内置的联动机制。

核心做法：所有 Store 组成一个树形结构，子节点可以通过 getRoot 获取根节点的引用，从而访问其他 Store。

✅ 优点：

  • 结构化：提供了规范化的 Store 组织和访问方式。
  • 内置能力：支持时间旅行、持久化、补丁监听等高级特性。
  • 类型安全：对 TypeScript 支持良好。

❌ 缺点：

  • 学习成本高：引入了新的概念和 API。
  • 侵入性强：整个应用都需要基于 MST 的范式构建。

适用场景：大型、复杂应用，需要严格的状态结构和高级功能。

方式六：使用 mobx-react 的 Provider + inject

这是 mobx-react 库提供的历史悠久的依赖注入方式，基于 React 的旧版 Context API 实现。

✅ 优点：

  • 避免了组件树的逐层传递（prop drilling）。
  • 支持 mapperFunction，可以只注入需要的部分数据。

❌ 缺点：

  • 已过时：官方现在推荐使用 React 的 useContext + createContext。
  • 仅适用于 React，非 React 环境无法使用。

适用场景：维护较老的 MobX + React 项目。

⚠️ 注意事项与最佳实践

  • ⚠️ 避免循环依赖：绝对不要让 Store A 依赖 Store B，同时 Store B 又依赖 Store A。
  • ⚠️ 注意初始化顺序：在 RootStore 的 constructor 中，不要在子 Store 的 constructor 里访问其他尚未初始化完成的子 Store。
  • ✅ 明确划分职责：每个 Store 应该只负责管理自己领域的状态和逻辑。
  • ✅ 善用 computed：如果一个 Store 需要的数据可以完全由另一个 Store 的状态推导出来，可以在本 Store 中创建一个 computed 属性，直接读取另一个 Store 的数据，而不是手动同步。
  • ✅ 保持架构清晰：对于大型应用，可以考虑将共享状态提升到 RootStore 层面，或将通用逻辑提取到独立的工具函数或服务中。

📊 总结与选型建议

联动方式 复杂度 耦合度 SSR 支持 测试友好度 推荐场景
Root Store 模式 中 中 ✅ ✅ 中大型应用首选
Singleton 单例 低 高 ❌ ❌ 小型项目/工具类
方法级 DI（参数传递） 低 低 ✅ ✅ 临时性/一次性调用
reaction 响应式联动 中 中 ✅ ✅ 自动同步场景
MST 高 中 ✅ ✅ 大型/复杂应用
Provider + inject 中 中 ✅ ✅ 维护旧项目

总而言之，Root Store 模式是 MobX 多 Store 联动的基石。它通过一个中心化的根 Store 来管理所有子 Store 的创建和通信，为应用状态的管理提供了一个清晰、可预测且易于维护的架构。

简单来说：

  • 简单的单例导入适合小型或原型项目。
  • 依赖注入适合处理临时的、方法级的依赖。
  • Root Store 模式则是构建中大型、可维护应用的黄金标准。
