一个 TCP 连接能发几个 HTTP 请求？

一个 TCP 连接能发几个 HTTP 请求？

先说结论：理论上无限，实际上取决于 HTTP 版本。

很多人面试时会被问到这个问题，答案其实藏在 HTTP 协议的演进史里。从 HTTP/1.0 的”一发一断”到 HTTP/3 的 QUIC 多路复用，每一代协议都在回答同一个问题：如何更高效地复用一条连接？

下面按版本逐一拆解。

HTTP/1.0：一发一断

HTTP/1.0 默认一个 TCP 连接只发一个 HTTP 请求，响应结束后立即断开。

工作流程很直接：

  1. 建立 TCP 连接（三次握手）
  2. 发送一个 HTTP 请求
  3. 接收响应
  4. 立即关闭连接

问题显而易见：建连成本太高。一个网页有 10 张图片，就要经历 10 次”握手—传输—断开”，时间和资源都浪费在连接管理上。

后来一些浏览器引入了非标准的 Connection: keep-alive 头试图复用连接，但这并非官方标准，且受服务器超时配置（如 KeepAliveTimeout）限制，并非无限复用。

HTTP/1.1：持久连接成为默认

HTTP/1.1 把 Connection: keep-alive 变成了默认行为。一次请求-响应结束后，TCP 连接保持打开，等待下一个请求。

  • 工作方式：客户端按顺序一个接一个地发送请求，通道在响应后保持空闲。
  • 关闭方式：任一方发送 Connection: close，或连接空闲超时后被关闭。

但 HTTP/1.1 有两个硬伤：

① 队头阻塞（Head-of-Line Blocking）

单个连接虽然可复用，但请求必须串行执行——前一个响应没回来，后一个请求就得排队。如果第一个请求是个大文件，后面所有请求都会被它堵住。

② 复用并非无限

服务器通常会配置上限：比如 Nginx 的 keepalive_requests 默认 100 个请求，keepalive_timeout 默认 65 秒。请求数达到上限或空闲超时，连接就会被关闭。

HTTP/2：多路复用

HTTP/2 是革命性的一步：它允许在一个 TCP 连接上同时交错发送多个请求和响应。

实现方式是二进制分帧：请求和响应被拆成更小的帧（Frame），每个帧打上流（Stream）ID。不同流的帧可以在同一条连接上混合传输，接收方按流 ID 重新组装。

带来的好处：

  • 解决了 HTTP 层面的队头阻塞——慢请求的帧不会堵住其他请求的帧
  • 一个 TCP 连接就能加载整个页面，省去多次握手的开销
  • 更充分地利用 TCP 带宽

但限制依然存在：HTTP 层不堵了，TCP 层还会堵。TCP 保证数据包按序送达，一旦某个包丢失，整条连接都要等它重传，所有 HTTP/2 流都会被阻塞。这就是所谓的 TCP 队头阻塞。

HTTP/3：基于 QUIC，彻底告别队头阻塞

为了干掉 TCP 层的队头阻塞，HTTP/3 直接弃用 TCP，改用基于 UDP 的新协议 QUIC。

QUIC 在 UDP 之上实现了自己可靠的、有序的传输机制，但顺序保证只到”流”这一级：某个流丢包只影响该流本身，不会波及连接上的其他流。

优势：

  • 同时解决 HTTP 层和 TCP 层的队头阻塞
  • 连接建立更快（通常 0-RTT 或 1-RTT），高延迟网络下优势尤其明显

一张表总结

HTTP 版本 底层连接 单连接请求数 核心限制因素 关键特性 主要问题
HTTP/1.0 TCP 1 个（默认）/ 有限个（keep-alive） 无默认长连接、超时配置 短连接，无复用 连接无法复用，开销巨大
HTTP/1.1 TCP 多个（串行） keepalive_requests、超时 长连接，串行复用 HTTP 队头阻塞
HTTP/2 TCP 海量（并行） 最大并发流数、服务器资源 二进制帧，多路复用 TCP 队头阻塞
HTTP/3 QUIC（over UDP） 海量（并行） 服务器资源、QUIC 配置 QUIC 多路复用，无队头阻塞 暂无明显通用性问题

写在最后

回到最初的问题：一个 TCP 连接能发几个 HTTP 请求？

  • HTTP/1.0：1 个（默认）
  • HTTP/1.1：多个，但串行，且受服务器配置限制
  • HTTP/2：海量并行，但受 TCP 层拖累
  • HTTP/3：海量并行，且无队头阻塞

协议演进的主线，其实就是一句话：让一条连接承载更多请求，同时让它们互不阻塞。 理解了这条主线，这个问题也就不再是死记硬背的面试题了。
