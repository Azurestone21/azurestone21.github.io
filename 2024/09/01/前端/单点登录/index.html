一、基础概念

1. 同源策略

同源 = 协议 + 域名 + 端口 完全相同。

父页面 子页面 是否同源
https://a.com https://a.com/sub 是
https://a.com https://sub.a.com 否（子域不同）
https://a.com http://a.com 否（协议不同）
https://a.com https://a.com:8080 否（端口不同）

同站：可注册主域相同。
例：cloud.example.com 与 imarketing.cloud.example.com 同站，但跨源。

2. Cookie 与 localStorage 隔离

特性 Cookie localStorage
隔离维度 域 + 路径，可设 Domain 跨子域 严格按 Origin 隔离
跨子域共享 可以（Domain=.example.com） 不可以
JS 可读 非 HttpOnly 可读 同源可读
自动随请求发送 是 否
跨源 iframe 读父的 不能 不能

3. iframe 访问规则

父：https://cloud.example.com
子：https://imarketing.cloud.example.com
→ 同站，跨源。

资源 同源 iframe 跨源 iframe
window.parent.localStorage 可访问 不可访问，报 SecurityError
window.parent.document.cookie 可读非 HttpOnly 不可读
自己的document.cookie 可读非 HttpOnly 可读自己域的非 HttpOnly
自己的localStorage 共享 按 Origin 隔离，不共享

注意：

  • sandbox 无 allow-same-origin 时，即使同源也受限。
  • document.domain 已废弃，不要依赖。

二、跨标签与跨域通信

方案 跨标签 跨源 说明
BroadcastChannel 是 否 同源多标签实时通信，推荐
localStorage + storage 事件 是 否 同源，兼容旧浏览器
SharedWorker 是 否 同源共享连接/状态
Service Worker 是 否 PWA、推送、同源广播
window.postMessage 是（需引用） 是 跨域 iframe、弹窗、OAuth
MessageChannel 是 是 点对点通信
WebSocket/SSE 是 是 跨源跨标签，服务端中转

选型：

  • 同源多标签同步：BroadcastChannel > localStorage + storage。
  • 跨域 iframe/弹窗：window.postMessage，必须校验 origin。
  • 跨域独立标签：前端无直接方案，走 WebSocket/SSE/服务端中转。

三、SSO 核心与前端角色

1. 定义

集中认证，分散会话：用户在认证中心登录一次，即可访问多个互信业务系统。

2. 角色

角色 职责
认证中心 IdP 统一登录、维护全局会话、发 code/ticket
业务后端 用 code 换 token、验证 token、建立局部会话、写 Cookie
业务前端 路由守卫、跳转、回调、请求拦截、多标签同步、登出

前端不实现认证，是 SSO 接入方。真正鉴权在后端。

四、OIDC 与授权流程

1. OAuth 2.0 vs OIDC

OAuth 2.0 OIDC
目的 授权 认证（用户是谁）
核心凭证 Access Token ID Token + Access Token
Token 格式 不强制 ID Token 必须是 JWT
典型场景 调用 API 登录、SSO

2. ID Token

JWT，由 IdP 签名。必须校验：

  • 签名（通过 jwks_uri 获取公钥）
  • iss（签发者）
  • aud（客户端 ID）
  • exp（过期时间）
  • nonce（防重放）

3. 授权码 + PKCE 流程（推荐）

  1. 前端生成 state、nonce、code_verifier，计算 code_challenge。
  2. 跳转认证中心：
  3. IdP 有全局会话则直接发 code，否则让用户登录。
  4. 重定向回 https://app.com/callback?code=xxx&state=xxx。
  5. 前端校验 state，把 code 和 code_verifier 交给后端。
  6. 后端换 id_token 和 access_token，验证后建立局部会话（通常写 HttpOnly Cookie）。
  7. 前端调 /api/me 拿用户信息，恢复回跳地址。
  8. 其他系统接同一 IdP，因全局会话存在可静默拿 code，实现免登。

六、Cookie 与 fetch 跨源细节

1. Domain 共享 Cookie

  • 请求匹配子域时，浏览器自动带上。
  • 但 JS 不能跨源读对方独有的 document.cookie。
  • Domain 共享的非 HttpOnly Cookie，两个子域都能通过 document.cookie 读取。
  • HttpOnly Cookie 任何时候 JS 都读不到，但请求会自动发送。

2. fetch/XHR 跨源与凭据

关键区分：

  • Cookie 的 Domain/Path/Secure/SameSite 规则决定“哪些 Cookie 有资格被带”。
  • 请求的 credentials 模式决定“这次请求允不允许带 Cookie”。
请求类型 默认 credentials 默认是否带匹配 Cookie 能否读响应
<img> / <script> / <iframe> / 表单 / 跳转 include 带 否/极有限
同源fetch / XHR same-origin 带 是
跨源 fetch / XHR same-origin 不带 是（需 CORS）

为什么跨源 fetch 默认不带？
安全设计：防止恶意脚本跨源读取敏感数据。<img> 等无法读响应，风险可控；fetch 能读响应，必须双重确认。

让跨源 fetch 带 Cookie 的条件：

  1. 前端：fetch(url, { credentials: 'include' })

  2. 服务端 CORS：

    （不能为 *）

  3. SameSite 允许。

3. HttpOnly 与 js-cookie

  • js-cookie 无法绕过 HttpOnly。
  • 如果代码能通过 Cookie.get 读到 token，说明该 Cookie 没有设置 HttpOnly。
  • 若设置了 HttpOnly，Cookie.get 返回 undefined，请求时浏览器仍自动携带。
  • 敏感 token 应放 HttpOnly + Secure + SameSite Cookie，前端不直接读。

验证方法：

  • Network 看 Set-Cookie 是否有 HttpOnly。
  • 控制台执行 document.cookie 或 Cookie.get('token')。
  • DevTools → Application → Cookies 查看 HttpOnly 列。

七、安全要点

  • 全站 HTTPS。
  • Cookie：HttpOnly、Secure、SameSite。
  • state 防 CSRF，nonce 防重放，PKCE 防授权码截获。
  • redirect_uri 必须白名单。
  • postMessage 校验 origin，发送指定精确 targetOrigin。
  • Token 尽量后端保存，前端不放长期 refresh_token。
  • 路由守卫只是体验，真正鉴权在后端。
  • 单点登出要清全局会话和局部会话。
  • 前端不解析 ID Token 当可信信息，应由后端验签后返回用户信息。

八、面试口述版

SSO 核心是集中认证、分散会话。前端不负责认证，主要负责接入。以 OIDC 授权码 + PKCE 为例：用户访问页面，路由守卫发现没登录，生成 state、nonce、code_verifier，跳转认证中心。认证中心有全局会话就直接带 code 回来；没有就让用户登录。回调页校验 state，把 code 交给后端换 token。后端验证 id_token 后建立局部会话，通常写 HttpOnly Cookie。前端再调用户信息接口，恢复原页面。其他系统接同一认证中心，因全局会话存在可静默拿 code，实现免登。后续请求靠 Cookie 或 Authorization，401 则刷新或重新登录。登出时调认证中心登出，清本地状态，并用 BroadcastChannel 同步多标签。安全上注意 state、nonce、PKCE、redirect_uri 白名单，token 不放 localStorage。

同域可直接共享父域 Cookie；跨域必须走认证中心重定向。前端不能跨域读认证中心 Cookie 和 localStorage。SPA 用 PKCE，生产更推荐 BFF。路由守卫只是体验，真正鉴权在后端。多标签登录态同步用 BroadcastChannel。OIDC 的 ID Token 是 JWT，必须验签、校验 iss、aud、exp、nonce，不能直接信。

九、关键结论速查

  • 同源 iframe：可读父系统 localStorage 和非 HttpOnly Cookie。
  • 跨源 iframe：不能直接读，只能 postMessage 或后端中转。
  • Domain=.example.com：Cookie 可跨子域共享，请求匹配子域自动带上。
  • 跨源 fetch/XHR：默认不带 Cookie，需 credentials: 'include' + CORS 允许。
  • js-cookie 能读到 token → 该 Cookie 没有 HttpOnly。
  • SSO 前端：路由守卫、跳转 IdP、处理回调、请求拦截、多标签同步、登出。
