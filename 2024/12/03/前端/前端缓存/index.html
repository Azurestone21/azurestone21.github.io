前端缓存

前端缓存

前端缓存大致分两块：浏览器本地缓存（cookie、localStorage、sessionStorage、indexDB）和 HTTP 缓存（强缓存、协商缓存）。前者是 JS 可读写的数据存储，后者是浏览器对 HTTP 响应的缓存复用机制，二者定位不同。

一、浏览器本地缓存

1. cookie

  • 大小限制约 4KB。
  • 主要保存登录态等信息，一般由服务器通过 Set-Cookie 响应头生成，浏览器随后在请求头 Cookie 中自动带回。
  • 可设置失效时间（Expires / Max-Age），默认浏览器关闭后失效（会话 cookie）。
  • 每次同源请求都会自动携带，所以 cookie 过多会增大请求体积。
  • 默认情况下，Cookie 在同源且路径匹配的页面间共享。如果服务器在设置 Cookie 时指定了 Domain 属性（例如 .example.com），那么该 Cookie 可以在该域名及其子域名（如 a.example.com 与 b.example.com）之间共享。只要满足上述域名和路径规则，同一浏览器内所有标签页的请求都会自动携带相同的 Cookie。

关键属性：

属性 作用
HttpOnly 禁止 JS 通过 document.cookie 读取，防 XSS 窃取
Secure 仅在 HTTPS 下发送
SameSite=Strict/Lax/None 限制跨站携带，防 CSRF；None 必须配合 Secure
Domain / Path 限定生效的域名和路径
Max-Age / Expires 有效期，Max-Age 优先级更高

2. localStorage（本地缓存）

  • 大小一般 5MB（各浏览器略有差异）。
  • HTML5 新增。
  • 持久保存，除非手动清除（localStorage.clear() 或用户清理浏览器数据）。无痕/隐私浏览模式下，数据会在最后一个隐私标签页关闭时被清除，且不与普通模式共享。
  • 只在浏览器本地保存，不参与服务器通信。
  • 同源共享，同步 API，存大量数据会阻塞主线程。

3. sessionStorage（会话缓存）

  • 大小一般也是 5MB。
  • 仅在当前会话有效，关闭标签页/页面即失效。
  • 同源、同标签页隔离：新开标签页不共享（即使同源）。
  • 同样不参与服务器通信。

4. indexDB

  • 浏览器端的事务型 NoSQL 数据库，容量远大于 localStorage（通常按磁盘配额，可达数百 MB 甚至更多）。
  • 支持异步 API（不阻塞主线程）、索引、事务、存储二进制（Blob/File）。
  • 适合存储大量结构化数据，如离线应用数据、缓存接口响应、富文本草稿等。
  • 同源共享，需通过 indexedDB.open() 打开数据库。

四者对比

特性 cookie localStorage sessionStorage indexDB
大小 ~4KB ~5MB ~5MB 大（按配额）
生命周期 可设，默认会话 永久 会话（关页面失效） 永久（除非删除）
参与请求 是（自动携带） 否 否 否
API 同步/异步 同步 同步 同步 异步
存储类型 字符串 字符串 字符串 结构化/二进制
典型用途 登录态 偏好设置 临时表单 大量离线数据

Service Worker 缓存（Cache Storage）是另一种前端可编程缓存，可拦截请求、自定义缓存策略，常与 PWA 配合，和 HTTP 缓存是并列关系。

二、HTTP 缓存

HTTP 缓存主要针对 HTML、CSS、JS、图片等资源，把请求过的响应存下来，再次需要时直接复用，减少网络请求。

优点：

  1. 减少不必要的网络传输，节约带宽。
  2. 加快页面加载。
  3. 降低服务器负载。

缺点（修正表述）：

  1. 可能读到旧资源，造成缓存不一致（这是最主要的代价）。
  2. 缓存会占用浏览器内存或磁盘空间（强缓存可能落内存也可能落磁盘）。
  3. 缓存策略配置不当会增加调试难度。

缓存存放位置

强缓存命中时，资源可能来自：

  • Memory Cache（内存缓存）：快，但随页面/进程销毁，通常用于当前页面已加载的资源。
  • Disk Cache（磁盘缓存）：持久，容量大，跨会话可用。

DevTools Network 面板会显示 200 (from memory cache) 或 200 (from disk cache)。

强缓存

强缓存命中时，浏览器完全不发请求，直接读本地。由两个响应头控制，优先级 Cache-Control > Expires；Cache-Control 内部 max-age 优先级高于 Expires。

Expires（已废弃）

设定一个绝对时间，在此时间前从缓存读取。判断机制是拿本地时间与 Expires 比较。

问题：本地与服务器时间不同步时，会出现资源无法缓存或永远被缓存。不推荐使用。

Cache-Control（替代 Expires）

HTTP/1.1 新增，用相对时间 max-age 解决时钟不同步问题。

常用指令：

指令 含义
max-age=N 客户端缓存 N 秒
s-maxage=N 共享缓存（CDN/代理）缓存 N 秒，优先级高于 max-age
no-cache 可以缓存，但每次使用前必须向服务器验证（走协商缓存）
no-store 禁止任何缓存，不存储
public 可被浏览器和代理服务器缓存
private 只允许浏览器缓存，代理不缓存
must-revalidate 过期后必须验证，不能用过期缓存
immutable 有效期内即使刷新也不验证，适合带 hash 的静态资源
stale-while-revalidate=N 过期后 N 秒内先用旧缓存，同时后台更新（补充）

易错点：no-cache ≠ 不缓存，而是”要验证”；no-store 才是”别存”。

浏览器刷新行为的影响（补充，高频考点）

操作 强缓存 协商缓存
地址栏回车 / 点链接 生效 生效
F5 / Ctrl+R 跳过（带 max-age=0） 生效
Ctrl+Shift+R 跳过 跳过（带 no-cache，直接请求）

协商缓存

强缓存过期后，浏览器带”验证凭证”问服务器，命中返回 304 Not Modified，响应体为空，只更新缓存元数据，省流量。

优先级：ETag/If-None-Match > Last-Modified/If-Modified-Since。

关键区分：强缓存是否过期由浏览器本地比较时间判断；协商缓存是否命中由服务器比较凭证判断。

Last-Modified / If-Modified-Since

  • Last-Modified：资源最后修改时间，服务器写入响应头。
  • If-Modified-Since：浏览器下次请求带上上次的 Last-Modified 值。
  • 服务器比较：资源更新了 → 200 + 新资源；没更新 → 304 走缓存。

实现方式：

  1. 服务器读出文件修改时间，写入响应头 Last-Modified。
  2. 同时设置 Cache-Control: no-cache（或让强缓存过期）。
  3. 强缓存过期后，浏览器带 If-Modified-Since 请求；服务器与当前 Last-Modified 比较，决定 200 或 304。

缺点：

  1. 仅凭修改时间判断，内容没变但修改时间变了（如改文件名再改回）会导致缓存失效。
  2. 修改时间最小单位是秒，几百毫秒内的修改可能检测不到，导致内容变了却返回 304。

ETag / If-None-Match

文件指纹：根据文件内容计算的唯一哈希值，内容变则指纹变。

HTTP/1.1 新增，把”比时间”改成”比指纹”。

实现方式：

  • 资源过期后，浏览器发现响应头有 ETag，请求时带 If-None-Match: <ETag 值>。
  • 服务器比对，相同 → 304；不同 → 200 + 新资源。

缺点：

  1. 计算指纹有服务端开销，文件大、数量多、计算频繁时影响性能。
  2. 分强验证和弱验证：
    • 强验证：任一字节变化即生成不同哈希，最精确，但计算量大。
    • 弱验证（W/"..."）：提取部分属性生成哈希，快但准确率低，会降低协商缓存有效性。

两句话总结：

  • Cache-Control 是 Expires 的完全替代方案。
  • ETag 不是 Last-Modified 的完全替代，而是补充方案（时间精度不够时用指纹兜底）。

三、实际项目中的常见策略

资源类型 推荐设置
HTML 入口文件 Cache-Control: no-cache + ETag，每次验证，保证拿到最新资源引用
带 hash 的 JS/CSS/图片 Cache-Control: public, max-age=31536000, immutable，文件名变 URL 就变，天然破缓存
敏感接口数据 Cache-Control: no-store
普通接口数据 短 max-age + ETag，或 no-cache 每次验证
CDN 层 s-maxage 控制边缘节点缓存，public 允许共享缓存

四、总结

本地缓存解决”数据存哪、存多久、是否随请求发送”；HTTP 缓存解决”响应能否复用”——强缓存决定要不要发请求（浏览器本地判断），协商缓存决定发了请求要不要传内容（服务器判断）。静态资源用长 max-age + hash，入口 HTML 用 no-cache + 验证，是最稳妥的组合。
