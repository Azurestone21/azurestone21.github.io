跨域

跨域

一、概述

1. 什么是同源？

同源指：协议、域名、端口 三者完全相同。

当前页面 请求地址 是否同源
http://localhost:8080 http://localhost:8080/api ✅ 同源
http://localhost:8080 https://localhost:8080/api ❌ 协议不同
http://localhost:8080 http://localhost:3000/api ❌ 端口不同
http://a.com http://b.com ❌ 域名不同

2. 什么是跨域？

当页面所在的源和请求目标的源不同源时，就是跨域。

跨域是浏览器行为，不是服务器行为。浏览器出于安全考虑，实施同源策略，限制 JS 读取跨域响应。

注意：服务器与服务器之间不存在跨域限制，只有浏览器里的 JS 发请求才会受限。

  • 简单请求：浏览器直接发出真实请求，服务器也可能处理了，但响应缺少 CORS 头，浏览器不把结果交给 JS。
  • 非简单请求：浏览器先发 OPTIONS 预检，预检不通过，真实请求根本不会发出。

所以在 Network 面板可能看到：

  • 简单请求：只有一个请求，但控制台报 CORS 错误。
  • 非简单请求：先有一个 OPTIONS，再有一个真实请求；如果预检失败，只有 OPTIONS。

3. 常见现象

  • 浏览器能访问接口，但 JS 请求报错。
  • Postman 能请求成功，浏览器里失败。
  • 请求返回 200，但 JS 拿不到数据。
  • 带自定义头或 Content-Type: application/json 时，多出一个 OPTIONS 请求。

三、解决方法

1. CORS（跨域资源共享，推荐）

CORS 是浏览器在同源策略基础上开的一个受控口子，让服务器声明哪些跨源请求可以读取响应。它管的是 JS 能不能读取跨源响应，不是请求能不能发出去。

常见响应头：

响应头 作用
Access-Control-Allow-Origin 允许的源，如http://localhost:8080 或 *
Access-Control-Allow-Methods 允许的方法，如GET, POST, PUT, DELETE, OPTIONS
Access-Control-Allow-Headers 允许的请求头，如Content-Type, Authorization
Access-Control-Allow-Credentials 是否允许携带 Cookie，true / false
Access-Control-Max-Age 预检结果缓存时间，单位秒
Access-Control-Expose-Headers 允许 JS 读取的响应头

如果 Access-Control-Allow-Credentials: true，则 Access-Control-Allow-Origin 不能为 *，必须是具体域名。

2. 代理（开发和生产常用）

浏览器请求同源地址，由代理服务器转发到真实后端。服务器之间没有同源策略。

开发环境：Vite / Vue CLI / webpack devServer 配置代理。

生产环境：Nginx 反向代理。

前端请求 /api/user，Nginx 转发到后端，浏览器认为是同源。

3. JSONP（历史方案，仅 GET）

利用 <script> 标签不受同源策略限制，通过回调函数接收数据。

缺点：只支持 GET，安全性差，现在基本不用。

4. WebSocket

WebSocket 不受同源策略限制，但需要服务端支持，且不是普通 HTTP 请求。

5. postMessage

用于 iframe、窗口之间的跨域通信，不是 HTTP 请求方案。

6. document.domain（仅主域相同）

例如 a.example.com 和 b.example.com 可以设置 document.domain = 'example.com'，现在已不推荐。

四、预检请求（Preflight）

1. 什么是预检请求？

当浏览器认为跨域请求是非简单请求时，会先发一个 OPTIONS 请求，询问服务器是否允许真实请求。这个 OPTIONS 就是预检请求。

2. 简单请求 vs 非简单请求

简单请求必须同时满足：

  • 方法为 GET、HEAD、POST。
  • 请求头只包含安全头：
    • Accept
    • Accept-Language
    • Content-Language
    • Content-Type，且值只能是：
      • application/x-www-form-urlencoded
      • multipart/form-data
      • text/plain
    • Range 等少数头。
  • 没有自定义请求头。

非简单请求：只要不满足上面任意一条，就会触发预检。常见：

  • 方法为 PUT、DELETE、PATCH。
  • Content-Type: application/json。
  • 带了自定义头，如 Authorization、Token、X-Requested-With。

Access-Control-Max-Age: 86400 表示预检结果缓存 86400 秒。
在缓存时间内，同样的请求不会再发 OPTIONS，直接发真实请求。

五、POST 请求在浏览器中为什么会有两次请求？

1. 不是所有 POST 都会两次

简单 POST：只发一次。

这种 Content-Type 属于简单请求，不会触发预检，所以 Network 里只有一个 POST。

2. 非简单 POST 会两次

只要 POST 满足以下任意一条，就会触发预检：

  • Content-Type: application/json
  • 带了自定义头，如 Authorization
  • 其他非简单头

浏览器会先发：

  1. OPTIONS /user —— 预检请求
  2. POST /user —— 真实请求

所以在 Network 面板看到两次请求。

3. 为什么设计预检？

预检是为了安全：
让服务器有机会决定是否允许跨域的真实请求，避免恶意站点直接发送复杂请求或携带凭据的请求。

4. 预检请求的特点

  • 不携带请求体。
  • 不携带 Cookie（即使前端设置了 withCredentials，预检请求本身也不带凭据）。
  • 由浏览器自动发起，前端无法直接控制。
  • 预检通过后，真实请求才会发出。

七、总结

问题 答案
什么是跨域？ 协议、域名、端口任一不同，就是跨域。
跨域是谁的限制？ 浏览器同源策略，服务器之间没有。
跨域表现？ 控制台 CORS 报错，请求可能发出但响应被拦截。
解决方法？ CORS、代理、JSONP、WebSocket、postMessage。
预检请求是什么？ 非简单请求前，浏览器自动发的OPTIONS 请求。
什么时候触发预检？ 非简单请求：PUT/DELETE/PATCH、Content-Type: application/json、自定义头等。
POST 为什么两次？ 非简单 POST 会先发OPTIONS 预检，再发真实 POST。简单 POST 只发一次。
预检缓存？ Access-Control-Max-Age 控制，缓存期间不再发 OPTIONS。
携带 Cookie？ 前端withCredentials / credentials: 'include'，服务端 Allow-Credentials: true 且 Allow-Origin 为具体域名。

一句话：跨域是浏览器的同源策略限制；解决主要靠 CORS 和代理；非简单请求会先发 OPTIONS 预检，所以 application/json 的 POST 在 Network 里通常看到两次请求。
