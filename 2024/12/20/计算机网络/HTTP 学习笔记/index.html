HTTP 学习笔记

HTTP 学习笔记

1. HTTP 概述

HTTP（HyperText Transfer Protocol，超文本传输协议） 是万维网中用于传输超文本、图片、JSON、文件等资源的应用层协议。浏览器作为 HTTP 客户端，通过 URL 向 Web 服务器发送请求；服务器处理请求后返回响应。HTTP 通常基于 TCP/IP 传输，HTTP/3 则基于 QUIC/UDP。

常见 Web 服务器包括 Apache、Nginx、IIS 等。HTTP 默认端口为 80，HTTPS 默认端口为 443。HTTPS 不是一个新的“HTTP 版本”，而是 HTTP over TLS，即用 TLS 保护 HTTP 通信。

HTTP 的核心特性可以概括为：

  • 客户端-服务器架构：客户端发起请求，服务器返回响应。
  • 无状态：协议本身不记忆上一次事务。需要保持登录态、购物车等状态时，通常借助 Cookie、Session、Token 等机制。
  • 媒体独立：只要客户端和服务器知道如何处理，任何类型的数据都可以通过 HTTP 传输。具体类型由 Content-Type 标注，其值通常是 MIME/媒体类型。
  • 可缓存、可分层：HTTP 允许缓存、代理、网关等中间组件参与通信。
  • 连接模型随版本演进：HTTP/1.0 默认短连接；HTTP/1.1 默认持久连接；HTTP/2 在同一连接上多路复用；HTTP/3 基于 QUIC。

注意：早期资料常把 HTTP/1.0 的“每次请求后断开连接”描述为“HTTP 是无连接”。这是历史说法，不是 HTTP 的现代准确定义。HTTP 本身是无状态协议；HTTP/1.1 默认使用持久连接，并不要求每个请求后立即断开。

一个简化的通信流程是：

graph LR
A[浏览器/HTTP 客户端] -->|HTTP 请求| B[Web 服务器]
B --> C[应用程序/CGI/Servlet/后端服务]
C --> D[数据库或其他服务]
D --> C
C --> B
B -->|HTTP 响应| A

2. HTTP 版本演进

版本 时间 主要特点
HTTP/1.0 1996 默认短连接，每个请求通常重新建立 TCP 连接；一个连接主要处理一个请求/响应；头部和缓存能力较弱。
HTTP/1.1 1997/1999，后续有 RFC 7230 系列、RFC 9110 系列更新 默认持久连接（Connection: keep-alive 成为默认行为，不需要显式开启）；支持 Host、缓存控制、分块传输等；同一连接上可依次发送多个请求，但仍可能存在 HTTP 级队头阻塞。
HTTP/2 2015，RFC 7540，后由 RFC 9113 更新 二进制分帧；同一 TCP 连接上多路复用多个请求/响应；使用 HPACK 压缩头部；曾定义服务器推送，但主流浏览器已移除支持，不宜作为现代主要优势。
HTTP/3 2022，RFC 9114 基于 QUIC/UDP；使用 QPACK 压缩头部；减少 TCP 层队头阻塞影响，支持更快的连接建立与多路复用。

需要区分几个概念：

  • HTTP/2 多路复用解决的是 HTTP/1.1 的 HTTP 级队头阻塞，但底层 TCP 丢包仍可能造成阻塞。
  • HTTP/3 基于 QUIC，进一步处理传输层阻塞问题。
  • HTTPS 是 HTTP 与 TLS 的组合，不是 HTTP/1.1、HTTP/2、HTTP/3 之外的“另一个版本”。HTTP/2 和 HTTP/3 都可以运行在 HTTPS 场景中。
  • HTTP/2 的头部压缩算法是 HPACK，不是“HIPAC”。

3. HTTP 消息结构

HTTP 消息分为请求消息和响应消息。HTTP/1.x 的消息是文本格式；HTTP/2 及 HTTP/3 使用二进制帧传输，但语义保持一致。

4. 请求方法

HTTP/1.0 定义了 GET、POST、HEAD；HTTP/1.1 增加了 OPTIONS、PUT、DELETE、TRACE、CONNECT；PATCH 由 RFC 5789 单独定义，不是 HTTP/1.1 最初新增的六种方法之一。

方法 说明 安全 幂等
GET 请求获取目标资源，通常返回响应正文。 是 是
HEAD 与 GET 类似，但响应中不返回正文，只返回头部，常用于检查资源是否存在、是否修改。 是 是
POST 向服务器提交数据，可能创建资源、触发处理或修改状态。 否 通常否
PUT 用请求体表示的内容替换目标资源的当前表示；多次相同 PUT 通常效果一致。 否 是
DELETE 请求删除目标资源。 否 是
CONNECT 建立隧道，常用于代理场景，例如通过代理建立 HTTPS 隧道。 否 否
OPTIONS 查询目标资源支持的通信选项/方法，常用于能力发现和 CORS 预检。 是 是
TRACE 回显服务器收到的请求，主要用于诊断；有安全风险，生产环境常禁用。 是 是
PATCH 对资源进行局部修改；由 RFC 5789 定义，不保证幂等。 否 不一定

说明：

  • 安全方法指语义上只读、不改变服务器状态的方法，如 GET、HEAD、OPTIONS、TRACE。
  • 幂等指执行一次和执行多次相同请求，对服务器状态的效果相同。幂等不等于响应完全相同。
  • GET 的请求体在 HTTP 语义中没有普遍定义的用途，实践中应避免用 GET 携带请求体。

5. 状态码

5.1 状态码分类

分类 含义
1xx 信息性响应，服务器已收到请求，需要请求者继续或切换协议。
2xx 成功，请求被成功接收、理解并处理。
3xx 重定向，需要进一步操作才能完成请求。
4xx 客户端错误，请求有语法错误或无法完成。
5xx 服务器错误，服务器在处理请求时发生错误。

5.2 常见状态码

状态码 英文名称 中文说明
100 Continue 继续。客户端可继续发送请求体或继续请求。
101 Switching Protocols 切换协议，例如升级到 WebSocket 或更高版本协议。
200 OK 请求成功。
201 Created 已创建新资源，常配合 Location 返回新资源地址。
202 Accepted 已接受请求，但尚未处理完成。
204 No Content 成功处理，但响应无正文。
206 Partial Content 部分内容，常用于范围请求。
301 Moved Permanently 永久重定向，资源已永久移动到新 URI。
302 Found 临时重定向。历史上部分客户端可能将 POST 改为 GET。
303 See Other 查看其他地址，通常要求客户端用 GET 访问 Location。
304 Not Modified 资源未修改，用于缓存验证；响应不应包含正文。
307 Temporary Redirect 临时重定向，要求保持原请求方法。
308 Permanent Redirect 永久重定向，要求保持原请求方法。
400 Bad Request 客户端请求语法错误，服务器无法理解。
401 Unauthorized 请求需要认证，或认证失败；常配合 WWW-Authenticate。
403 Forbidden 服务器理解请求但拒绝执行；与 401 不同，403 通常不是“未认证”。
404 Not Found 服务器找不到目标资源。
405 Method Not Allowed 目标资源不支持该请求方法；常配合 Allow。
406 Not Acceptable 服务器无法根据客户端的内容协商条件生成可接受响应。
408 Request Timeout 服务器等待客户端请求超时。
409 Conflict 请求与资源当前状态冲突。
410 Gone 资源曾经存在但已永久删除。
411 Length Required 服务器要求请求包含 Content-Length。
412 Precondition Failed 请求先决条件失败，常用于条件请求。
413 Content Too Large 请求内容过大，服务器拒绝处理。旧称 Request Entity Too Large。
414 URI Too Long 请求 URI 过长。旧称 Request-URI Too Large。
415 Unsupported Media Type 服务器不支持请求体使用的媒体类型。
416 Range Not Satisfiable 请求的范围无效。
418 I’m a teapot 玩笑/保留状态码，不适合作为正式业务语义依赖。
422 Unprocessable Content 请求格式正确但语义无法处理；旧称 Unprocessable Entity。
425 Too Early 服务器不愿处理可能被重放的早期请求。
426 Upgrade Required 客户端需要升级协议。
428 Precondition Required 服务器要求请求携带先决条件。
429 Too Many Requests 请求过多，触发限流。
431 Request Header Fields Too Large 请求头字段过大。
451 Unavailable For Legal Reasons 因法律原因不可用。
500 Internal Server Error 服务器内部错误。
501 Not Implemented 服务器不支持请求的功能。
502 Bad Gateway 网关或代理从上游服务器收到无效响应。
503 Service Unavailable 服务暂不可用，可能因过载或维护；可配合 Retry-After。
504 Gateway Timeout 网关或代理等待上游服务器超时。
505 HTTP Version Not Supported 服务器不支持请求使用的 HTTP 版本。
511 Network Authentication Required 网络需要认证，常见于强制门户。

补充：305 Use Proxy 已废弃，306 未使用。状态码表不必死记全部，重点是掌握分类、常见语义以及 301/302/307/308、401/403、502/504 等区别。

6. 常用 HTTP 头部字段

HTTP 头部字段很多，下面列出常见且重要的字段。实际开发中应以 RFC 9110 等规范和 MDN 文档为准。

字段 方向 说明
Host 请求 HTTP/1.1 中通常必需，指定目标主机和端口，用于虚拟主机。
Connection 请求/响应 控制连接选项，如 close。HTTP/1.1 默认持久连接。
Cache-Control 请求/响应 缓存策略，如 no-cache、max-age、no-store。
ETag 响应 资源版本标识，用于条件请求和缓存验证。
If-None-Match 请求 携带 ETag，服务器可返回 304 表示未修改。
Last-Modified 响应 资源最后修改时间。
If-Modified-Since 请求 条件请求，服务器可据此返回 304。
Vary 响应 告诉缓存按哪些请求头区分响应，如 Vary: Accept-Encoding。
Location 响应 重定向目标或新资源地址，常与 3xx、201 配合。
Set-Cookie 响应 设置 Cookie。
Cookie 请求 客户端回传 Cookie。
Authorization 请求 携带认证凭据，如 Bearer Token。
WWW-Authenticate 响应 401 响应中说明认证方式。
Accept 请求 客户端可接受的响应媒体类型。
Accept-Encoding 请求 客户端可接受的内容编码，如 gzip、br。
Accept-Language 请求 客户端可接受的自然语言。
Content-Type 请求/响应 说明消息体的媒体类型，如 application/json、text/html; charset=utf-8。
Content-Length 请求/响应 消息体字节长度。分块传输时通常不使用。
Content-Encoding 请求/响应 内容编码，如 gzip、br；与 Transfer-Encoding 不同。
Transfer-Encoding 请求/响应 传输编码，如 chunked；与 Content-Length 通常互斥。
Content-Language 响应 响应内容的自然语言。
Content-Disposition 响应 控制内容以内联展示还是附件下载，如 attachment; filename="a.pdf"。
Allow 响应 目标资源支持的方法，常配合 405。
Date 响应 消息生成时间。
Server 响应 服务器软件信息，常由服务器自动设置。

说明：

  • Content-Encoding 管的是内容压缩/编码，如 gzip；Transfer-Encoding: chunked 管的是消息传输分块。两者不是一回事。
  • Content-Type 主要声明媒体类型；字符编码通常通过 charset 参数、HTML <meta charset>、BOM、规范默认值等共同决定，不能简单说“Content-Type 决定一切编码”。
  • Refresh 不是 HTTP 正式规范中的标准头，属于历史扩展，不应作为通用协议字段讲解。
  • 原材料中大量 Servlet API 描述属于实现示例，不宜混在 HTTP 协议头定义中。

7. Content-Type 与 MIME/媒体类型

7.1 两者的关系

Content-Type 是 HTTP 头部字段；MIME 类型/媒体类型是这个字段所装载的值。

可以理解为“容器与内容”的关系：

  • Content-Type 是容器：告诉接收方消息体是什么类型。
  • 媒体类型是内容：具体标识数据格式，如 text/html、application/json、image/png。

MIME 最初来自电子邮件系统，全称是 Multipurpose Internet Mail Extensions。现在更准确的称呼是媒体类型（Media Type），由 IETF RFC 6838 定义和标准化。HTTP 借用了 MIME 的媒体类型标准，并通过 Content-Type 头部字段来标注消息体的类型。

Content-Type 可以出现在请求和响应中：

  • 请求中：说明请求体的媒体类型，如 POST 提交 JSON 时的 Content-Type: application/json。
  • 响应中：说明响应正文的媒体类型，如 Content-Type: text/html; charset=utf-8。

7.6 Content-Type 与编码、压缩的区别

需要区分三个概念：

概念 相关字段 作用
媒体类型 Content-Type 说明消息体是什么格式，如 HTML、JSON、PNG。
字符编码 Content-Type 的 charset 参数等 说明文本使用什么字符集，如 UTF-8。
内容编码/压缩 Content-Encoding 说明内容是否经过 gzip、br 等压缩。
传输编码 Transfer-Encoding 说明消息如何分块传输，如 chunked。

因此，不能笼统地说 Content-Type 决定浏览器以什么编码读取文件。它主要声明媒体类型；编码和压缩还涉及其他字段和规则。浏览器在缺失或错误设置媒体类型时，还可能进行 MIME 嗅探。

7.7 内容协商

HTTP 内容协商让客户端表达偏好，服务器选择合适的表示：

客户端请求头 对应的服务器响应头 说明
Accept Content-Type 客户端可接受的媒体类型。
Accept-Encoding Content-Encoding 客户端可接受的内容编码。
Accept-Language Content-Language 客户端可接受的自然语言。
Accept-Charset Content-Type; charset 已过时，现代场景很少使用。

服务器可用 Vary 告诉缓存：响应会随哪些请求头变化。例如 Vary: Accept-Encoding 表示缓存应按 Accept-Encoding 区分不同压缩版本。

8. MIME 嗅探与安全

8.1 MIME 嗅探

当响应缺失 Content-Type、类型设置错误，或浏览器认为类型不可信时，浏览器可能通过查看资源内容来猜测其类型，这叫 MIME 嗅探。不同浏览器、不同上下文的行为可能不同。

MIME 嗅探有安全风险：某些类型可被浏览器执行或解释，而服务器可能本意是让用户下载。服务器可以发送响应头：

X-Content-Type-Options: nosniff 是响应头，用于阻止浏览器进行 MIME 嗅探。它不是请求头，也不是通过 Content-Type 请求头来设置的。

8.2 与 CORS 的关系

在 CORS 中，简单请求对 Content-Type 有限制：只允许 application/x-www-form-urlencoded、multipart/form-data、text/plain 三种。使用 application/json 等类型通常会触发预检请求。这是浏览器安全模型对 Content-Type 使用方式的额外约束，不改变 HTTP 对 Content-Type 的定义。

8.3 安全建议

  • 不要将不可信用户上传的内容以 text/html 或 image/svg+xml 在同源下直接提供，以免 XSS。
  • 下载场景可使用 Content-Disposition: attachment 配合合适的 Content-Type。
  • 对未知二进制可使用 application/octet-stream，但要注意浏览器行为差异。
  • 对 JSON 接口使用 application/json，不要用 text/html 返回 JSON。
  • 静态资源服务器应正确配置常见扩展名到媒体类型的映射。
  • 对脚本、样式、字体等资源，正确设置媒体类型并考虑 nosniff。

说明：媒体类型与扩展名不是一一对应的强绑定关系。服务器可以根据配置把某个扩展名映射为某种媒体类型；浏览器也可能进行 MIME 嗅探。实际项目中应以 IANA 媒体类型注册表、MDN 文档和服务器配置为准。

10. 总结

  • HTTP 是应用层协议，基于客户端-服务器模型，核心特性是无状态、媒体独立、可缓存、可分层。
  • HTTP/1.1 默认持久连接；HTTP/2 使用 HPACK、二进制分帧和多路复用；HTTP/3 基于 QUIC/UDP，使用 QPACK。
  • 请求方法、状态码、头部字段的定义来自 HTTP 规范；浏览器和 Web 标准会在 HTTP 之上增加安全与行为约束。
  • Content-Type 是 HTTP 头部字段，其值是 MIME/媒体类型。它主要声明消息体的类型，不单独决定字符编码和压缩。
  • MIME/媒体类型由 RFC 6838 定义，语法为 type/subtype，常用于 Content-Type、Accept 等头部。
  • MIME 嗅探可能带来安全风险，服务器可用响应头 X-Content-Type-Options: nosniff 降低风险。
  • CORS 简单请求对 Content-Type 有三种限制；application/json 通常会触发预检请求。
